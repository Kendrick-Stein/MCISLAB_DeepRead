### HarnessDev
- **Title**: HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?
- **Institutes**: ByteDance Seed, Singapore University of Technology and Design, Georgia Institute of Technology, M-A-P, TokenWave.AI
- **Source**: [link](https://arxiv.org/abs/2609.01437)  📰 HF Daily ⬆️ 229   **📒 论文笔记**: [[Papers/2609-HarnessDev]]
- **核心**: 把评测对象从 agent 的任务输出换成 agent 赖以运行的 harness 本身：六个 creator LLM 拿同一个跑得通但全 benchmark 得 0 的 weak seed，先从零写 harness（4 domain / 5 benchmark / 2,207 instance），再用下游执行反馈迭代改自己的 harness，creator 与 executor 严格分离，harness 冻结后才评测。Creation 的结论是域间落差极大，写作追平、MLE-bench 超过所选参照，code 与 search 落后，最好的 Opus 4.8 平均 67.8。Evolution 才是真正的结果：同 commit 重跑方差约 ±4.75 分，64 次官方版本切换里 27 次的增益落在噪声带内、只有 2 次有超噪声带的正向证据，可见反馈与 held-out 同向率 53.1%，9 条 lineage 里只有 2 条 declare 出了 held-out 最优版本。配套的 artifact 审计发现大量"设计"从未进入执行路径：108 个 code component 有 18 个零触发且全属 state/memory，26,679 条轨迹零 checkpoint 事件。
- **锐评**: 这篇最值钱的不是任何一个分数，是 creator / executor 分离这条设计线，以及它测出来的一件此前只被抱怨、从未被量化的事：LLM 写出来的 harness 主要是在给自己量体裁衣，不是在写通用执行基建。Opus 的 SWE-Pro 从 69.3 掉到 33.0、Search harness 的 duplicate-query 率从 10.1% 飙到 88.2%、某个 code harness 把 120 步上限硬编码在原 executor 周围换人就崩——这组数说的是停止规则和去重逻辑长成了特定 executor 的形状；反过来 Qwen 的 harness 换更强 executor 后 BrowseComp 涨 17.6，说明原来的瓶颈根本不在 harness。零分 weak seed 是配套的干净地板设计，任何非零分都能归因到 creator 加的执行逻辑，这一点比大多数 agent benchmark 讲究。而 artifact 审计是我近期见过信息密度最高的一节：124/587 个 Writing feature 是 dead code、169 个新函数里 25 个无调用者、2,325 个 Data 任务里 441 个产出退化 submission 而没有任何一个 harness 察觉、failed Data 任务 77.8% 归因于 harness 缺陷而非 executor 能力。这套"查声明的组件到底跑没跑"的方法论，可以直接搬去审任何一篇 self-evolving 系统论文，我预期它比这篇的 benchmark 本身活得更久。

  但这篇的正向结论和它自己的证据标准是打架的，而且是同一节里打。论文一边用 ±4.75 的重跑噪声带把 64 次版本切换中的 27 次判死，一边转头报"五条 self-runtime lineage held-out 全部改善、+1.43 到 +4.44、均值 +3.11"——这些增益跟那条噪声带同量级，每个 cell 只有一条轨迹，而 held-out-630 的重复运行方差论文压根没测。用自家的尺子量，"self-runtime 下 evolution 有效"这句话应该读成"未被排除"而不是"已被确认"。负向那半不受影响，证伪只要反例，GPT-5.5 那条 −10.32 就够硬。人类参照行则更糟：Table 3 里三个带星数字是从 OpenAI GPT-5.6 release report 抄来的外部结果、作者没自跑，每个 benchmark 还配着不同的 harness–executor 组合（SWE-Pro 配 Claude Fable 5、Terminal-Bench 和 BrowseComp 配 GPT-5.6 Sol），executor 本身就比六个 creator 强，所以 67.8 vs 86.2 里同时混着 harness 质量差和模型能力差。更刺眼的是 Avg 列是四项非加权均值、把 MLE-bench 排除在外，而 MLE-bench 恰好是模型唯一超过参照的那一域——作者在正文承认了口径，但选出来的这个组合方向一致地让差距更大。加上 Creation 是 avg@3、多个单元含一个塌掉的 replica，剔除后 Opus SWE-Pro 从 33.0 变 49.1、GPT-5.5 的 EQ-Bench3 从 46.5 变 69.7，Unified-Eval 的排名有相当一部分是"这三次里有没有抽到崩的那一把"决定的。n=3 撑不住这个方差，主表就别拿来排座次。

  设计上还有两处硬伤。第一，Evolution 只做 code，而 Creation 的结论明明是 search 落后最多、最需要看迭代能不能救回来的就是 search；held-out 又只覆盖 SWE-Pro，反馈信号却是 SWE-Pro-100 和 Terminal-Bench-89 的等权均值——等于对着两条腿优化、只审计一条腿的泛化，另一条腿的 post-freeze 证据是空的。第二，整篇论文小心翼翼地把 creator 和 executor 拆开，却让开发环境跟着 creator 变（五个用 Claude Code 2.1.177，GPT-5.5 用 Codex 0.144.3），这个变量和 creator 身份完全混淆且没有交叉设计——一篇论证"harness 决定成败"的论文，自己给 creator 配的 harness 不统一，这个自指的讽刺作者没有正面处理。归因也停在相关层："revision call 相关 0.57 而 self-test 只有 0.13–0.26"很有意思，但能读懂失败并定点修改的模型本来就更强，这条相关不足以支撑因果版本；何况专用的 trajectory 诊断接口全程只被调用过两次，creator 大多在自写脚本和小 probe（而一个 GPT-5.5 候选过了全部 5 个 Terminal probe、全集只有 0.584），所以测到的与其说是"LLM 能不能演化 harness"，不如说是"LLM 在一个它基本不用的诊断接口下能不能演化 harness"。至于 state 缺口，26,679 条轨迹零 checkpoint 可以是模型不会写，也可以是 500 步 / 7,200 秒上限下的任务根本用不着——两种解释处方完全相反，加一个强制中断续跑的任务族就能分开，论文没做。代码也还没放，seed、审计脚本、held-out split 全是 "will be released"。最后说句公道话：这篇真正会被引的是它的负面结论——在可见分数上选版本的效果跟掷硬币差不多（53.1% 同向、2/9 最优），这一刀砍在所有以 held-in score 做 accept gate 的 self-evolving 流水线上；而且它顺带留了个作者自己没接的问题：held-out 最优版本确实存在于轨迹里，只是选不出来，那么瓶颈就不是"改不改得好"而是"认不认得出改好了"。
- **Rating**: `3` 🔥 formulation 与审计方法都是新的，且负面结论（同向率 53.1%、2/9 declared 最优、组件零触发）直接改写读所有 self-evolving harness 论文的方式——尽管它的正向结论按自家噪声标准应当作废。

### Aspire
- **Title**: Aspire: Can Models Self-Evolve from Vague Goals?
- **Institutes**: ByteDance Seed, Singapore University of Technology and Design, M-A-P, TokenWave.AI
- **Source**: [link](https://arxiv.org/abs/2608.31111)  📰 HF Daily ⬆️ 207   **📒 论文笔记**: [[Papers/2608-Aspire]]
- **核心**: 现有 self-evolution 研究都是在人类把"提升数学能力"翻译成"刷高 AIME"之后才开始的，agent 只搜 how to improve，不决定 what to optimize。Aspire 把这一步（target operationalization）撤掉：只给一句自然语言模糊目标，agent 自己选数据、定训练方法、造验证信号，最后由 520 道专家新撰、agent 完全不可见的隐藏题外部裁决。结果是三连负：final-only 协议下 12 个 model–goal pair 只有 1 个 Avg@2 超过 base（45.33→48.00），24 个 run 里 21 个被回滚；adaptive-feedback 的 30 个 cell 只留下 1 个改进，而作者自己把它降级为"feedback-guided selection"；权重冻结下三个自造 harness 全部低于人工 Qwen-Agent 参考（28.64 → 27.22 / 20.76 / 19.32），第四个 creator 干脆没造出合法 harness。一句话总结全文：训练环闭合了（28/30 cell 跑完 data–train–verify），能力环没有。
- **锐评**: 先说值得抄的部分——这篇的度量纪律在 self-evolution 这个重灾区里罕见地干净。三处自我设限直接把行业惯用的糊弄手法堵死了：保留增益恒非负被明说成 rollback 的 selection outcome 而非学习证据；best evaluated / selected / retained 三种分数分开报；唯一那个留存正例被作者主动降格。更狠的是它把参照系从"上一个 checkpoint"换成了 base model，于是 4B Self 的数学 lineage 0.79 → 1.75 → 2.38 这条漂亮的单调上升曲线，在 base 17.86 的水平线下方全程趴着——所谓"自我进化"大量是从训练自伤中往回爬。62 次 transition 拆成 28 升 13 平 21 降、14/22 的后续搜索超过首个 checkpoint，这组数字比任何 headline 都值钱。失败诊断也到了机制层而不是停在"效果不好"：21,000 个单数字 SFT target → 279 个单数字评测输出 → 得分 0/0/0/6.141/0，是可复现的格式坍塌链；Terra harness 漏掉 final-answer invariant、calculator 调用后提交 342/520 字符残稿，两道题从 75.00/52.33 掉到 2.57/2.91，算术上占该次执行跌幅约 70%。负增益的组件归因比正增益好做，因为失败路径稀疏可定位——这一点被这篇无意中示范了。

  但标题问的是 "Can Models Self-Evolve"，证据说的是 Qwen3.5-4B 和 9B 不行。被更新权重的始终是这两个小模型，"一个 4B 被自选的 numeric-label MMLU SFT 打到答案格式坍塌"和"当前最强模型无法从模糊目标自演化"根本是两个命题，论文自己限定得很老实，但下游引用者一定会把这层限定吃掉。RQ1 那组对照更是不干净到作者自己都承认：27.07 vs 官方 32.90 里混着 prompt 改写和系统配置差异，而 task 级方向不一致（vague-goal 在 HumanEval 56.63 vs 47.33、BFCL 58.63 vs 47.13、GSM8K 74.35 vs 69.48 反而更高）恰恰是混杂的病征而不是噪声——一个真"模糊目标致降分"的效应不该在三个任务上反号。这一节只能当过程侧描述读。然后是贯穿全文的 N=1：adaptive-feedback 5×6 每 cell 一次，RQ3 每个 condition 一条 creation trajectory，那三次执行测的是冻结 harness 的运行时抖动而不是三次独立演化，per-execution 离散度压根没报。于是 Sol 的 27.22 vs 参考 28.64 这 1.42 分是不是噪声，文中无从判断——而"三个 successor 全部低于参考"这个最响的 headline 强度恰好压在这 1.42 上。同班底晚一天的 HarnessDev 报了 ±4.75 噪声带，反衬得这里的缺失更刺眼。

  最要命的开放问题是 gap 的归因：agent 在 30/32 次 dataset import 中不管目标是科学、逻辑还是写作一律拉 GSM8K/Hendrycks，Luna 在自造的 8 题 checklist 上满分就收工 40 分钟、代价是隐藏集最低的 19.32——这些看起来是缺"proxy 有效性自检"这一环，而不是模糊目标本身不可操作化。论文诊断出了病却没做那个对照实验：给 agent 一个 validation set 难度校准/相关性估计接口之后还差多少？不做这个，"目标形式太难"和"当前 scaffold 太笨"就永远绑在一起测。同理，RQ3 的结论和 DarwinX 的 harness 演化 75.5%→83.2% 直接对撞，而 Aspire 这边是一步 H0→H1、fitness 全靠自建 proxy、runtime 锁死 4B——三个变量同时不同，所以它能支持的结论只是"4B runtime 上的一次性 harness 生成 + 自建 checklist 会崩"，不是"harness 自演化不 work"。最后是 hidden evaluation 范式的结构性账单：六个 goal 分数量纲差到 health base 87.00 而 math base 17.86，judge 是 gemini-3.5-flash，题目按设计不公开、项目页也没放代码数据（唯一 artifact 就是一个 project page），"只有 1 个 cell 保留改进"这种跨异质切片的计数结论，外部无法独立验证难度校准和判分质量。它的价值来自不公开，它的可复现性也死于不公开。
- **Rating**: `3` 🔥 benchmark 本身会过时，但"把改进判给 base model 而不是上一个 checkpoint"这条参照系纪律，足以让人回头重读一整批自演化论文的 headline 增益。

### Repo-To-Skill
- **Title**: Repo-To-Skill: Distilling GitHub Repositories Into AI4AI Skills
- **Institutes**: Beijing Academy of Artificial Intelligence, University of Science and Technology of China, Renmin University of China, The Hong Kong Polytechnic University
- **Source**: [link](https://arxiv.org/abs/2609.02749)  📰 HF Daily ⬆️ 506   **📒 论文笔记**: [[Papers/2609-RepoToSkill]]
- **核心**: DisCo 把 operational knowledge 从 model backbone 和 harness 里切出来，当作 agent 的第三个可独立调节的变量。它走两条蒸馏路径——task-agnostic 把 1,000 个 ML 仓库压成 skill graph，task-oriented 按任务能力缺口现场找材料——每条 skill 必须通过 assertion-backed usability case 加仓库原生 test / CLI / smoke 检查才准入，最终得到 5,353 条 skill、20 areas、178 capability families 的 AREX-Skill Library。评测端固定 GPT-5.5（xhigh）与 vanilla Codex，唯一变量是开不开 skill：MLE-bench 全量 75 题 31.11 → 72.89，PaperBench 29.45 → 39.59（18 升 2 退），FrontierCS 70.63 → 77.14（95% CI [3.41, 9.83]），PassNet AS Score 1.343 → 1.5313、Correctness 81.35% → 90.76%。最有冲击力的一条是 72.89 越过公开榜首 Famou-Agent 2.0 的 64.44，而且没写一行自定义 orchestration。
- **锐评**: 先说值得肯定的：这篇的实验设计动作比绝大多数 harness 论文干净——固定 backbone、固定 harness、只换 `𝒦`，敢把知识当成一个可归因的自变量来测，而不是像同行那样报个 bundle 级增益就把归因甩给读者；准入门用可执行检查而不是 LLM 自评，比 [[Papers/2607-SkillKD]] 拿 evaluator 满分当判据要硬得多。但"+134.3%"这个数字是彻头彻尾的营销修辞：分母是 31.11 的裸 Codex，低于榜上任何一个正经 ML 研究 agent，连 R&D-Agent 都有 35.11。在一个被人为压低的基线上算相对提升，换个基线百分比立刻蒸发。真正有信息量的只有 72.89 > 64.44 这条绝对比较，可对手用的是 Gemini-3-Pro-Preview 和 Claude-Opus-4.6，backbone 都不同，这不是受控对照，而 GPT-5.5 上的强 harness 对照点论文既没做也拿不到。

  更难看的是记账。"matched running budget" 指的是 per-task 上限相同，不是实际算力配平——FrontierCS 上带 skill 条件实打实多烧了 1.82× token、1.59× steps、1.62× tool calls。作者拿 Spearman ρ≈0.006/0.014/0.015 来挡，但那只证明**跨任务**的增量用量与增量收益不相关，完全不能排除**条件之间**的系统性算力差；缺的对照极其便宜——让裸 Codex 也跑到 4.47M token 看能涨到多少——却没做。构建端更是直接搬出账本：约 \$40/repo × 1,000 repo ≈ \$4 万，声称是一次性摊销尚可接受，可 MLE-bench 那个头条数字用的是**逐任务**构建的 task-oriented skill，每任务每阶段另配 ≤24 GPU-hours 的独立预算。也就是说，全文最亮的 72.89 恰好来自唯一一个"构建成本根本没法摊销"的设定。这条边界论文写在 Table 5 和附录里，正文的 budget 叙事却读起来像固定预算下的免费午餐。

  最致命的是全文零消融——独立核验确认 "ablat" 出现 0 次，scope / ground / construct / verify 四个阶段一个都没被单独关掉。verification gate 是本文最强的设计主张，却没有 with/without 对照，于是"经过验证的 skill 比同样文本但未验证的 skill 强多少"这个决定成败的问题完全悬空；如果差距很小，这篇的贡献就退化成"把 README 和文档整理进 context"。task-agnostic 与 task-oriented 也从未在同一 benchmark 上对打。最接近消融的 Table 6 是 skill graph 版本迭代 v1 vs v2，还为省钱换成了 Claude Code + DeepSeek v4 pro，既不隔离阶段也不同源。对照一下 [[Papers/2606-Resource2Skill]]：来源、结构、检索、规模四轴正交消融，同类工作里的实验卫生标杆——本文在结果规模上碾压它，在机制解释上被它按在地上。另外三处失败模式指向同一件事：PaperBench 2 篇回退、FrontierCS 只在 74/188 上改善、PassNet 的 Fast_1 反降（注意这条 Fast_1 数字在笔记 Ledger 中标为 C21、未纳入本轮独立核验，引用需谨慎），合起来像是检索到的 skill 挤掉了 agent 自己会找的窄解法并把行为推向保守。最后提醒读者，这篇笔记的 `verification_status` 是 `partial`：C13 的代码许可声明已被降级为 unsupported（CC BY-NC-SA 4.0 是 arXiv 对**论文**的分发许可，仓库自身标 Apache-2.0，论文根本没声明代码许可），C21 未独立核验；污染控制也只做了"按来源排除"的浅层动作，skill 从 web search 蒸馏而来，Kaggle 通用 winning recipe 和 related work 里对目标 method 的复述能不能被挡住，论文没给任何检测证据。
- **Rating**: `2` 👀 数字够猛且归因框架干净，但零消融让核心机制（verification gate）完全没被验证、构建成本被移出记账，属于值得盯紧、不值得当基础共识的工作。

### SolarWM
- **Title**: SolarWM: Open Data and Scalable Training for Long-Horizon Video World Models
- **Institutes**: CUHK-SZ, SLAI, NUS, CUHK, HKUST, HKUST-GZ, NVIDIA, UCLA, MSRA
- **Source**: [link](https://arxiv.org/abs/2609.02886)  📰 HF Daily ⬆️ 134   **📒 论文笔记**: [[Papers/2609-SolarWM]]
- **核心**: 把 interactive video world model 从数据到长时程推理整条链路开源：data engine 将 10 个来源、1.43M clip 归一成带 metric 相机位姿/内参、caption、质量度量与拒绝理由的统一契约，876k 保留、549k 连同失败原因一并发布，并把 physical corpus / logical recipe / model view 三层显式分开。模型侧用同一套 fused-PRoPE 相机条件加 bidirectional adaptation → teacher-forced AnyFlow → DMD 三段配方，在 Wan2.2、LTX-2.5、MiniMax-H3 上做出 5B–33B 四条 backbone-native 路线，只用 5 秒序列训练就跑出 4 步采样、无 attention sink 的 60 分钟不间断 rollout。方法学上唯一的新主张是 TF-AnyFlow 让 Causal Forcing / Causal Forcing++ 各自需要的 Causal ODE、Causal CD 初始化阶段变得不必要。代价是 Experiments 全是采样帧：没有 FVD/VBench 一类指标、没有被打分的 baseline、没有 ablation、没有 human eval，也没有训练配置表。
- **锐评**: 数据那半篇是这批 world model 发布里最像样的工程。"先全量标注、再谈筛选"是正确的 factorization，把 rejected 分区连同机器可读的拒绝理由发出来，等于把选择策略从数据集里剥成可替换的一层——"放松运动过滤会怎样"这种问题在别处要重跑一遍昂贵的相机估计和 caption，在这里只是换一份 index。caption 里 hard-negative 掉相机运动和镜头术语，理由写得明白（否则 text condition 泄漏相机控制，模型分不清是 pose 让它动还是 caption 让它动），是少见的把数据决策讲成机制而不是玄学的做法。fused-PRoPE 只在 Q/K/V 上作 projective rotation、不加分支不加 attention pass，minimax-h3 那条只往 [96:128) 维度注入、把 [0:96) 的原生 MM-RoPE 原样留着，都是"不砸预训练表示"的具体活儿。

  然后另外半篇塌了。全文零定量评测，却在 Introduction 和 contribution 里各写一次 "achieve state-of-the-art performance"——对谁 state of the art？没有一个被打分的对照方法。abstract 和 conclusion 的 "real-time interaction" 同样一个延迟、吞吐、实测帧率都没有，16 fps 是生成视频的名义帧率，不是生成速度，把它当实时证据是偷换。更难堪的是 Introduction 那条 key finding："大部分优化应放在双向阶段，AR 适配收敛很快，DMD 需要的步数最少"——这是全文最容易证明的一句话，一条步数曲线或一张 GPU 小时表就完事，作者选择不给，之后再不回访。而唯一有分量的方法主张 TF-AnyFlow，恰恰是唯一没被隔离的东西：同一条 5B 路线上用 Causal ODE + Causal CD 初始化跑一遍 DMD 做对照，代码权重都在自己手里，就是没做。方法学新意压在一个点上，这个点没有实验。

  "跨 backbone 通用"这个卖点被训练阶段拦腰截断了。四条路线同框只出现在 Figure 6 的双向 10 秒 OOD 生成；因果适配、DMD 蒸馏、分钟级和小时级 rollout 的所有证据统统来自 wan2.2-5B-fast 一条。论文证明的是"共享数据与相机契约能让四个 backbone 都完成双向适配"，abstract 说的却是三段式配方通用——四分之一的证据撑一个整数的 claim。至于 60 分钟 rollout，作者给的验收标准是端点"remain recognizable and visually coherent"，稀疏采样帧上的可辨识性而已：没有闭环回起点的 revisit consistency，没有任何一致性指标，而 Clean Plate 早把人和车从语料里删干净了——世界里根本没有会出画再入画的动态主体，最难的那种失败模式在数据构造阶段就被过滤掉了。对比之下 Alaya-EVOKE 的两小时靠外部 geometric world state bank 且在 WBench 上报了数字，ABot-World-0 靠 bounded KV cache 报了分项（memory 维度 0.5041，难看但敢报），SolarWM 主张什么记忆机制都不要——三者里最激进的断言，配三者里唯一为零的测量。顺带说，Table 1 那张 18 系统发布矩阵里 SolarWM 自己每列打勾的行，caption 写明是"本次发布的承诺"，其他系统是 2026-08-18 的实际核对，这不是同一口径的比较，是自评混进对照表。还有个定性偏差：Clean Plate 删动态实体、caption 排除动作、唯一时变控制是预设相机轨迹，这套语料训出来的是可导航的场景外推器，不是 abstract 说的"响应 action 或语义指令"的 interactive world model；action-conditioned 监督被系统性地筛掉了。vault 侧站外核对（非论文内容）显示代码 Apache-2.0、四套权重已上线，但数据仓库约 2.73 TB 对不上正文 25.85 TB 的物理语料，目前公开的是标注、recipe 加部分 clip 归档——引用"完全开源"时得分层说。
- **Rating**: `2` 👀 数据引擎和 rejected 分区是真能被别人用起来的资产，但能力侧一个数字都没有，SOTA 和 real-time 两条 claim 直接落空，方法唯一亮点 TF-AnyFlow 无 ablation——当资源收藏，别当结论引用。

### EarlyEval
- **Title**: EarlyEval: Cheaper Agent Evaluation via Early Outcome Prediction
- **Institutes**: Shanghai Jiao Tong University · Singapore Management University · East China Normal University · Shanghai Innovation Institute
- **Source**: [link](https://arxiv.org/abs/2609.02783)  📰 HF Daily ⬆️ 112   **📒 论文笔记**: [[Papers/2609-EarlyEval]]
- **核心**: 现有的 agent 评测降本几乎都在砍任务数（Anchor Points、tinyBenchmarks 那条线），EarlyEval 换了一条正交的轴——每个任务少跑几步。做法朴素到近乎复古：把轨迹前缀映射成 435/517 维手工特征（行为计数、TF-IDF+SVD 文本、可选的 gold patch 重叠），离线用**其他 agent** 的历史轨迹训一对 LightGBM（success / failure 各一），Platt 校准后逐步打分，任一侧越过阈值就掐断 rollout，并把**预测标签直接当作该任务的真实得分**写进榜单。SWE-bench Verified / TerminalBench / Toolathlon 上 leave-one-agent-out 协议下，dual 配置省 17.7%–26.0% 步数、最多 44.1% input token，per-agent resolve rate 偏差 1–2 pp，Spearman ρ 0.959–0.994。作者自己划界：这套东西不用来产出可引用的 benchmark 分数，只服务于迭代开发时的反复重测。
- **锐评**: 问题选得比方法好，而方法居然也没输——这是它最值得夸的地方。RQ4 那张表把"该不该上 LLM judge"这件事做成了实证而非品味：Qwen-0.5B LoRA judge 保真度确实能打（90.7% accuracy、0.8 pp 失真），但只省 17.9% 步数，且每步一次前向的开销正好把 early stopping 省下的算力吃回去；LightGBM 亚毫秒推理拿 34.8% coverage、26.0% 步数节省。特征消融也自洽：去掉 Reference 族只从 34.8% 掉到 32.1%，去掉 Textual 族反而升到 35.9%，主力是 Behavioral——这既解释了它为什么能迁到没有 gold patch 的 benchmark，也顺手说明那 320 维 TF-IDF 基本是装饰。但从这里往下就全是问题。第一，"dual" 是包装，跨 benchmark 真正干活的只有 failure predictor 那一半：success head 出了 SWE-bench 就崩，TerminalBench no-same-scaffold 上 precision 61.4%–69.0%，Toolathlon 上 coverage 直接 0.0%，RQ2 的排序实验因此在两个 benchmark 上老老实实退回 failure-only。加性观察（dual 步数节省恰等于两个 single 之和，说明两 head 几乎从不在同一条轨迹触发）更坐实了这不是一个统一机制，而是两个各自为战、其中一个基本不出手的分类器。第二，也是最致命的：推荐操作点被定义为"使 Δ|Pass@1| 保持在 2 pp 内的最低阈值"，而 Δ|Pass@1| 只有跑完全程拿到真实 resolve rate 才算得出来——部署时面对一个没见过的 agent，你恰恰缺这个量。论文没有做"在训练轨迹上定阈值、在留出 agent 上兑现"的前瞻性实验（论文对此未加讨论，这是我的判断），于是 1–2 pp 这个卖点带着事后选择的成分，而数据明明都在手上。第三，LOAO 只留出 agent 不留出 task，每个 agent 都跑完整任务池，留出 agent 面对的任务在训练时已被别人跑过并带标签进了训练集——一个 96%+ precision 的失败判别器，究竟在读"这个 agent 正在往坑里走"还是在读"这道题历史上谁都做不出来"，缺 held-out-task 对照就永远说不清；而这两者的区别决定了分数下降到底是不是 agent 的锅。第四，fidelity 口径偏松：Spearman ρ 衡量整张榜的秩相关，而迭代开发要回答的是"我这版改动有没有变好"这种相邻小差距的成对判断，TerminalBench no-same-model 下 37 个 agent 只有 59% 保住确切名次，ρ=0.959 跟"能分辨相邻两个 agent 谁更强"完全是两回事。最后是报告口径的两处滑头：abstract 的 "13%–26%" 是拼出来的区间，下界 12.7% 取自 RQ2 的 failure-only 配置、上界 26.0% 取自 SWE-bench 的 dual 配置，四个推荐操作点的 dual 真实值是 17.7%–26.0%（Introduction 还另给了个 13%–25%）；而 "89%–97% prediction accuracy" 在表里根本没有对应的 dual accuracy 列，它更像 failure predictor 单 head 的 precision 范围被换了个名字端出来。数字逐条对得上原文，但组合方式让人把单 head 的 precision 读成整个系统的准确率。适用边界也要说清：三个 benchmark 全是 code/shell/tool-use，Behavioral 族里 17 维 error & test status 加上多数 event timing 信号，搬到截图为观察、没有 test suite 可解析的 GUI 或具身场景直接不存在——对我们关心的方向，这篇的价值目前是方法论启发，不是可直接复用的工具。
- **Rating**: `2` 👀 ，切口正交且诚实、"简单方法够用"被真的证出来了，但阈值用测试端真值挑、task 泄漏未隔离两个洞让所有 fidelity 数字都打折，且能力只覆盖 SWE 类文本轨迹。

### FailBench
- **Title**: FailBench: How Reliable are VLMs at Judging Robot Task Success?
- **Institutes**: Metric AI Lab
- **Source**: [link](https://arxiv.org/abs/2609.03611)  📄 arXiv   **📒 论文笔记**: [[Papers/2609-FailBench]]
- **核心**: 把 14 个独立采集的公开数据源（12 real + 2 sim，2,197 次尝试）压成同一道二分类题——给指令和录像，判这次操作成没成——沿用各源自带的 outcome label，75% 的失败是自然发生而非事后构造。13 个 VLM 判官里最强的 Gemini 3 Flash 只有 0.77 macro balanced accuracy，5 个专为 failure detection 微调的模型全部低于各自 base，且每个专用检测器都输给除最小通用模型外的所有通用 VLM。作者进一步把 RoboFAC-7B 的 published 0.806 拆成"按 960:244 类别先验重加权后的恒答 failure"，平衡子集上它 failure recall 1.000 / success recall 0.067，掉回随机。最后加了个不用训练的 evidence-localization pipeline，只裁输入视野，把 Gemini 从 0.773 抬到 0.797（McNemar p=0.0015）。
- **锐评**: 这篇的价值全在那个负结果和那把审计刀上，不在 benchmark 本身。"5 个专用检测器全部低于自家 base"是全篇内部效度最强的比较——只差微调一步，harness/prompt/帧预算全同——但别被"方向一致"骗了：五个 delta 是 −0.002 / −0.057 / −0.088 / −0.040 / −0.003，真正有量级的只有 3 个，Guardian 和 FailSense 就是平手，而 Table 7 连方差和置信区间都没有，全文唯一的推断统计量是 crop 那个 p 值。真正的杀器是 Appendix B.1/D 那套先验重加权：RoboFAC published 0.806 ≈ 恒答 failure 白拿的 0.797，ViFailback 的 445:55 split 上全判 failure 就有 0.890 而它报的 base 是 0.900——这是在说这条线上一批已发表数字是类别不平衡的产物，比 benchmark 本身更该被引用。硬伤也很实在：主榜和消融表在全部 14 个子集上都对不上，同一个 Gemma 判同样的全帧，roboarena 差 10.0 点（0.70 对 0.800）、reflect 差 9.7 点，macro 差 1.8 点；Sec 4.1 那句"most possible deterministic setting"大概率是原因，但论文从头到尾没对过账、没量化过 spread——而这个未声明的协议敏感性和它 +2.3 点的头条增益、以及 Guardian −0.002 是同一量级甚至更大。直接后果就是 abstract 里"contact-intensive assembly 上无模型超过 0.60"这条被论文自己的 Table 8（Baseline Gemma 0.608）和 Table 9（masked blackout 0.652）当场推翻，不能当结论引用。crop 干预也别吹：223 fix 对 160 break，净 +63/2166，14 个子集里 4 个变差（reflect −6.7、phail −4.5），对它自己诊断出的 contact 问题几乎无效（reassemble 0.567→0.591），换个 detector 就掉 0.01——这更像"框和判官的耦合运气"而非 abstract 说的"input-level intervention is effective"。还有两个洞：全文没有任何人类 balanced accuracy 基线或标注者一致率，25% 抽检只说"发现问题就换"却不给发现率，而标签映射全是作者再编码（rh20t 0-9 二值化、roboreward 刻意剔掉表示"接近完成"的 4 分、armnetbench 只留 π0.5），所以 0.77 里混了多少标签噪声完全无从判断；覆盖面清一色 tabletop 平行夹爪，最难的 contact-rich 子集本来录了 force-torque 却不用，于是"视觉判官在接触上接近随机"根本分不清是 VLM 不行还是视觉这个模态不够——而这两条后续路线完全相反。
- **Rating**: `2` 👀 ，问题选得对、类别不平衡审计手法可复用且杀伤力大，但 abstract 级断言被自家表格推翻、主榜与消融表全 14 子集对不上无人对账、且无人类上界，结论得打折读。
