### VLA-Feedback
- **Title**: Catch Me If You Can: Real-Time Feedback Denoising for Responsive VLAs
- **Institutes**: The University of Texas at Austin, University of Central Florida
- **Source**: [link](https://arxiv.org/abs/2609.21022)  📄 arXiv   **📒 论文笔记**: [[2609-VLAFeedback]]
- **核心**: action chunking 的老毛病是 chunk 执行期间观测被丢掉，后半段等于拿过期信息开环走。本文的做法是把 diffusion VLA 的最后一步去噪从"生成的收尾"改成"执行期的反馈接口"：冻结的 GR00T planner 跑完除最后一步外的全部去噪，输出 near-final chunk，之后每执行一个动作前，由一个 1.19M 可训练参数的模块用最新 hand-view 观测预测去噪速度，把这一个动作补完最后一步。调度是 1:16:16，planner 全程冻结，不重规划、不训第二个策略。三个动态 Robosuite 任务平均成功率 27.5% → 85.0%，静态 LIBERO 基本持平（Goal 92 打平、Object 97.5 → 95.5），真机 Franka 三任务平均 51% → 73%，已被 CoRL 2026 接收。
- **锐评**: 接口选得是真好，这是全文最值钱的一句话——修正发生在去噪速度空间，天然落在 planner 学到的流形方向上，而不是在最终动作上外挂一个不受约束的残差；1.19M 挂在 3B 冻结基座上，改动小到可以直接搬去别的 flow policy。更难得的是它把主 confound 自己切开了：保留 16 次高频更新、只拿掉观测输入这条消融，直接回答了"收益到底来自看见新观测还是执行频率变高"，同类工作十有八九会省掉这一步。动态任务也是真动态，目标执行期移动、每 2 s 离散换向。
  问题从标题那个 "Real-Time" 开始。Table 2 里那个 2 ms 只算模块自身运行时间，而附录 Table 5 的硬件实测端到端回路是 71.01 ms，其中 62 ms 是相机采集——系统响应上限由相机决定，反馈推理在里面根本不是瓶颈；控制频率本身也只有 10 Hz。附录给了诚实数字值得肯定，问题是进 abstract 和主表的是不含感知的那一个。
  最朴素的对照直接没做：同一 planner 缩短 chunk、或提高 replanning 频率，一个都没测，附录写得明明白白 "No intra-chunk replanning was used"。这条之所以要命，是因为 GR00T 规划器本身只要 80 ms，与 100 ms 控制间隔同量级；按笔记作者代入 Table 2 与 Table 5 推算，加回感知与通信后端到端约 149 ms、约 6.7 Hz，所以逐步重规划确实不免费——但它究竟输不输给反馈去噪，本文一个字没回答。related work 点名的 Real-Time Chunking、Leave No Observation Behind、Policy Decorator 三条直接竞争路线，实验里零复现，全靠作者自己实现的 Δa 残差消融当替身；"去噪空间优于动作残差"只能约束到本文实现，推广不到那几条线。
  数字也经不起细看。27.5% → 85.0% 是三个任务的算术均值，而那个 27.5% 的 GR00T 在两个动态任务上被降配过的 FiS-VLA 反超（2D 67.5 vs 20、drop-ball 80 vs 15）——受控归因没问题，但拿它当 headline 就有粉饰。baseline 整体高度非单调（OpenVLA 1D 仅 5 却在 2D 拿 60），更像某些策略碰巧走对了位置，而非闭环跟踪能力的差异；同一批任务对本方法的方差凭什么可以忽略？全文 40 rollout / 真机 20 rollout，零误差棒、零置信区间、零多种子，真机 51% → 73% 按笔记作者推算不过是 60 次试验里约 13 次的差异。FiS-VLA 因显存被冻视觉 backbone、LIBERO 只剩 41.5 / 53.5，"优于双系统"的结论因此比表面弱一档。消融（Fig. 5）只有柱状图没有数值表，四条结论只能引方向不能引数——偏偏这几条才是机制解释的支柱。最后，总去噪步数 K 与最后一步步长 Δk 全文都没给，那"一步到底够不够"根本无从评估；也没有任何 jerk / 平滑度指标来回应"逐步独立修正会不会抖"。Table 3 里 +40% 速度塌到 5%，作者写得诚实，但也把修正容量的天花板摆在了台面上。
- **Rating**: `2` 👀 ，接口抽象干净、主对照受控、关键 confound 自己切开了，但"real-time"靠不含感知的记账撑着、三条已发表竞争方法一条没比、消融只有图没有数，够得上值得关注，够不上必读。

### CommitFlow
- **Title**: CommitFlow: Semantic Commitment Verification and Local Correction for Long-Horizon Robot Manipulation VLA Execution
- **Institutes**: National University of Defense Technology
- **Source**: [link](https://arxiv.org/abs/2609.21908)  📄 arXiv   **📒 论文笔记**: [[2609-CommitFlow]]
- **核心**: 把 long-horizon VLA 的失败重述为一类 mismatch——policy 已推进到下一 stage，但本该建立的物理条件（semantic commitment）还没建立，于是后续动作从错误状态出发、偏差逐级传播。方案是三件套闭环：SCM（一个 GRU，不是大 VLM）核验 commitment 并按 (时间步, 通道) 粒度派发 Hold/Correct/Keep 权限；BoundaryFlow 在 rank-12 SVD 子空间里生成有界残差，并对 nominal 样本显式监督「输出零修正」；RGC 从候选增益里挑满足几何与关节约束的最小值。RoboTwin 2.0 上 π0.5 的 Avg.10 从 53.2 提到 75.9，但那四行 baseline 是引自 CAPS 论文的数字，作者自跑的同源证据是 Avg.11 的 49.4 → 72.8。真机只有 2 个任务。
- **锐评**: formulation 比方法值钱。「action command 本身无法确认一个物理条件是否已经建立」这句话是全文最硬的 insight，它一刀把 CommitFlow 和两类邻居划开：TACO/CAPS 那一路优化轨迹漂移，而漂移小不蕴含前置条件已满足；CycleVLA/FLARE 那一路 subtask 回退，粒度粗到会撤销仍然有效的抓握。介入点从 failure 之后提到 transition 之前，是有物理意义的时序判断，不是包装。约束设计也自洽：三值权限 + 低秩子空间 + $c_{\max}\tanh$ 硬上界 + null supervision + 最小可行增益，「最小干预」是写进目标函数的，不是口号。诚实度也在水准之上——LingBot-VLA 上 96 降到 93、IK ablation 把 Object Cabinet 从 61 拉到 57、regrasping 子集局部恢复 66.7% 而任务成功仅 46.7%，这些全报了。
  但硬伤三条。第一，**「frozen base policy」被 abstract 包装成了近乎免费，实际不是**：SCM 要标注 causal window，BoundaryFlow 要成对的 expert 修正演示，RGC 要成功轨迹做 P95 标定，每个 base policy 还得单配一个 correction head。成本只是从策略参数搬到了标注流水线。对照真 training-free 的 VLA-Corrector，性价比论证整个缺席。第二，**方法的承重墙是手工 adapter**：pre-alignment/reaching/grasp closure/lifting 四类模板以及每个模板下的 object、arm role、physical condition、后继 action 全是人写死的——所谓 semantic commitment 并没有被学出来，而是被解决在了 adapter 层。作者自己在 limitation 里承认这卡死了 open-ended 扩展，而「从 instruction + 观测推断 event 结构」才是这个 formulation 真正有意思的部分，本文没碰。第三，也是最致命的：**一个以「扣住动作」为核心机制的系统，从头到尾没报 commitment violation 的 precision/recall，没有误报率，没有 false hold 导致的超时/死锁统计**（Ledger C13 明确是全文检索无果）。false negative 放偏差过去、false positive 让任务停滞，代价完全不对称，却被下游成功率糅成一个数。更难看的是 stage recognition 的 Macro-F1 88.98% 掉在作者自己画的 95% 目标线以下——监控器远未饱和，而整个系统建在它的判断上。
  数字层面还有两处要扣。headline 的 +22.7 是跨来源比较（C3：RDT/π0.5/TACO/CAPS 引自 CAPS 论文），RoboTwin 2.0 带强 domain randomization，100-trial 成功率漂几个点很正常，强度该按 Table II 的 +23.4 读而非 Table I。更值得盯的是增益随 base 变强迅速衰减：π0 +16.4 / π0.5 +23.4 / LingBot-VLA 仅 +5.2——论文列了这条趋势线却拒绝讨论它意味着什么。如果 +5.2 才是强 base 上的典型量级，那整套 adapter + 双模块训练的账根本算不平。最后，ablation 的切法是歪的：Table III 三个变体全带 SCM，**没有任何一栏回答「gate 本身值多少」**。笔记作者据 Table I/III 跨表推算 gate + 重新 query 可能已吃掉约一半提升（约 +12.5 vs +13.2）——必须强调这是笔记作者的推算而非论文结论，且两表并非同一次运行（同 6 任务 Table I 均值 79.2 ≠ Table III 的 80.0）。但方向值得追：「在 checkpoint 无条件丢弃 stale action、用新观测重新 query base」这个几乎零成本的动作，是必须被排除的 confound。论文没做这个 baseline，而它恰恰可能是本文最有价值的发现。
- **Rating**: `2` 👀 ，formulation 值得留存、约束设计干净且负结果报得诚实，但核心检测器零误差量化、承重墙是手工 adapter、headline 跨来源且增益在强 base 上只剩 +5.2——是好问题的一版早期实现，不是答案。

### VLA-Scope
- **Title**: VLA-Scope: Shift-Aware Failure Prediction for Vision-Language-Action Models
- **Institutes**: Texas Tech University, Purdue University
- **Source**: [link](https://arxiv.org/abs/2609.21246)  📄 arXiv   **📒 论文笔记**: [[2609-VLAScope]]
- **核心**: 在冻结的 OpenVLA 外挂一套纯 logistic regression 的两段诊断器：初始化时用 pooled 图文 embedding 判 ID/OOD 并分七类 shift（ROC-AUC 0.9454、类型准确率 91.00%），执行中把 7 维类型 one-hot + 14 维动作前缀统计 + 32 维累计 hidden state PCA 拼成 53 维，滚动预测「这条 rollout 最终会不会失败」。LIBERO-Spatial 十任务、1,400 条合成 OOD rollout 上，step 60 的 ROC-AUC 0.8497，高于作者自行复现的 ActProbe（0.8132）与 SAFE（0.8055 / 0.7414），CPU 单次打分 0.893 ms，策略侧只多 2.15 ms 初始化开销。全部实验在仿真中完成，单一架构，无代码发布。
- **锐评**: 最值得记的一点是它自己的消融把标题拆了。论文叫 "Shift-Aware"，而 Table VI 的账是：承重的是累计表征（去掉掉 0.0591），shift 类型在已有动作特征之上只值约 0.015（Actions only 0.7756 → Actions+Type 0.7906），单独用类型只有 0.6739。一旦开始读执行证据，「偏的是哪一类」几乎不再提供信息——这是好的负面结果，可惜被摘要的叙事盖住了。
  Stage 1 那个 0.9454 的名字也起大了：七类扰动由 LIBERO-Plus 固定生成器产出，十折留出的是**任务**而非**类别**，每折训练侧都见过全部七种扰动。所以它衡量的是闭集识别「训练时见过的七个生成器」，不是部署时唯一会发生的那件事——发现一个没见过的偏移。数据全部现成，leave-one-category-out 的对照成本几乎为零，偏偏没做。
  「提前量」在这篇里同样是空的：预测目标是最终结局，没有 lead time 度量，也没把风险上升与失败发生时刻对齐。Table II 的 12.52% FPR 是「恰好第 60 步瞟一眼」的数，而更接近 monitor 真实行为的 ever-alarm 口径是召回 83.51% / 误报 50.73%——一半以上会成功的 rollout 先挨一次误警，差了四倍。Table III 那串 0.9699 / 0.9818 要预先知道最终长度 T，是事后分析不是预警；Table II 从 step 90 起 cohort 只剩 598→226→25→7 个存活成功，F1 冲上 90% 主要是类别比例在漂。全篇能支撑「积累执行证据有用」的只有 step 10/30/60 三行。
  还缺一个零参数对照：649/1,400 的失败率意味着「一律预测失败」的平凡规则 F1 = 63.35%（笔记作者据 C2/C21 推算，非论文数字），而 step 10 的 59.43% 低于它、step 30 的 66.73% 只高 3.4 个点，要到 step 60 才真正拉开。基线对比里还有一处不对称：ActProbe 吃的是 clip 到 [−1,1] 之后的 execution-side 命令，而 clip 恰好摧毁 ActProbe 赖以为生的动作幅值信息，本文自己用的却是 pre-transform 解码值——那 0.0365 的领先里有多少来自方法、多少来自输入表示，现有证据分不开。三个最该比的（Sentinel / FIPER / FAIL-Detect）引了没跑，FAIL-Detect 尤其刺眼，它的 conformal 时变阈值正好打在本文最软的地方：全程硬编码 0.5，而同一个 0.5 在 step 10 是 36.09% FPR、step 60 是 12.52%、step 160 又回到 52.00%。
  好的部分也别抹掉：三个 logistic regression 加一次 PCA 就干到这个水平，线性形式让 logit 差能精确拆成动作项与表征项，是可用的诊断接口而非修辞；**完全不干预执行**意味着它不像同族的适配层工作那样背着「额外执行预算」的归因污染。作者的诚实也超出 9 页短文的平均水准——主动报 cohort 变化、主动报 ever-alarm 误报、主动报去掉 gripper 反而略好。只是诚实不能替代未做的实验：门控漏掉的 216 条里有 45 条最终失败（约 6.9% 的失败一个分数都拿不到），hidden state 取法绑死自回归 token 策略，π₀ 一族的 flow-matching 动作头根本没有对应量，"general diagnostic framework" 目前只有一个架构的证据。
- **Rating**: `2` 👀 ，工程干净、自曝家丑到位，但标题卖点被自家消融证伪、闭集当开集、提前量未度量，属于值得读一遍的诚实小品而非必读。

### SoL-Pi
- **Title**: SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness
- **Institutes**: NVIDIA, NTU, MIT
- **Source**: [link](https://arxiv.org/abs/2609.20519)  🔥 HF Trending ⬆️ 95   **📒 论文笔记**: [[2609-SoLPi]]
- **核心**: 不改模型、不改 serving，只改 harness——模型与环境之间那层负责呈现状态、暴露动作、处理反馈的代码。研究 agent 读 base harness（Pi）的轨迹，在 535 个可执行环境上从 152 个方向里筛出四个机制：Action Fusion（编辑+验证合成一次 tool 调用）、Online Context Compact（把压缩挂到 plan step 边界并做成本闸门）、ObservationPack（大 observation 第三次起换成 handle + 摘录）、Evidence-Preserving Reducer（便宜模型抽 build/test 日志证据 + 确定性 verifier 校验）。EdgeBench 上全栈相对 Pi 削 49.0% token、33.2% 成本，分数从 44.83 掉到 42.00。harness 只在 GPT-5.6 Sol 轨迹上开发，零再搜索换到 Opus 5，效率增益仍在（−44.7% token / −33.5% 成本）。
- **锐评**: 先说真货：**搜索与评测的隔离是这篇唯一值得抄的部分**。指标、容差、验收规则在开跑前冻结且脱离被优化 agent 的控制，held-out 只用于单向拒绝、失败不回流触发再优化——这是对着 arXiv:2607.12227 那个"演化 harness 对搜索任务过拟合"的反例做的流程设计，不是事后 sanity check。cache 账本那条也是硬结论：cache-read 砍半、cache-write 翻倍、总成本仍降三分之一，说明只盯 prefix cache 命中率会做出错误决策，这条拿走就能用。产物是四段能单独读、单独移植、各自对应一个说得清的浪费来源的机制代码，而不是一坨演化到看不懂的配置，这比大多数 RSI 论文的产出体面得多。
  现在说问题。**第一，标题里的 "Recursively" 是虚假广告**。整个 pipeline 跑了一轮，SoL-Pi 从没被当成下一轮的起点 harness，作者自己在 §5.1 承认 recursive improvement 是"长期愿景"。以 RSI 为卖点、generation 数等于 1，这是这个赛道的通病，但挂在标题上就是另一回事了。
  **第二，"performance comparable to Pi" 出了 EdgeBench 就崩**。Terminal-Bench 4 上 15 题 vs Pi 的 18 题，相对少解 16.7%；IMO 2026 上 Codex 过 5 题、SoL-Pi 过 3 题。论文报的是"单解题成本更低"——这个指标在分母变小时会自动变好，少解 3 题同时少花 \$75，人均成本当然下来。这不是省钱，这是换了个分母。根因清楚：能力闸门约束的是搜索环境上的**聚合**指标，不约束逐任务回归，换到分布外 benchmark 立刻露馅。
  **第三，SoL-Pi [Performance] 是 selection-on-test**。它不是一个搜出来的配置，是按 backend 分别从 Table 4 里挑出的最高分单机制——GPT-5.6 Sol 挑 ObservationPack、Opus 5 挑 Action Fusion——而 Table 4 就算在 EdgeBench 上。前面那套隔离纪律保护的是四机制和 Efficiency 点，Performance 点直接用了评测集的数字。结论节那句"提升性能 5.3–12.8%"因此不该和 Efficiency 的证据等级并列。附带一提，51 个公开任务里有 11 题在冻结候选的单向验收中用过，headline 评测集有五分之一不是全新的。
  **第四，方差为零。** 全文无误差棒、无多 seed，swarm 实验明说每配置只跑一次。Table 4 里那些 2–5 分的差距——正是选 Performance 点的依据——落在一条没人测过的噪声带里；[[2609-HarnessDev]] 同 commit 重跑测到 ±4.75 分。token/成本那一侧（33%–49%）远大于任何合理噪声，是可信的；分数那一侧基本不可读。
  **两个必须点名的 evidence boundary**：摘要那个"每小时省 \$8.75–\$13.50"是 `abstract-only`，"hourly" 全文只出现一次，正文、表格、图注都没给折算口径（单任务时长、并发假设一概没有）——**这个最上头的数字推导过程不可核查**，笔记作者按 51 任务 × 2 小时反推能对上，但那是读者补的，不是论文写的。另外机构信息（NVIDIA/NTU/MIT）在 ledger 里标 `unsupported`，原文只印 "NTU" 缩写从未展开。
  还有一刀：**"跨 backend 迁移"验证的是跨 LLM，不是跨 harness**。四个机制全实现为 Pi 的扩展，三个依赖 Pi 特定接口（`update_plan` 的 plan 边界、Pi 的 file-mutation tool schema、Pi 的 observation 投影时机）。Codex、Claude Code、OpenCode 在论文里只当 baseline 行出现，没一个被当宿主试过。所以真正的绑定可能从"绑模型"换成了"绑 harness 架构"，而这个方向零数据点。最后一个没人算的账：Reducer 要调 GPT-5.6 Luna、Compact 要触发 Pi 原生 compaction，论文明说成本闸门"does not separately price the summarization call"，但没写清 \$894 含不含这些辅助调用——Reducer 那行 input 从 0.0011B 跳到 0.0051B（全表唯一 input 上升）大概就是它的痕迹。95 upvotes 里有相当一部分是"NVIDIA + RSI + 省钱三分之一"这个标题组合买来的。
- **Rating**: `2` 👀 ，隔离纪律和 cache 账本是真 insight、四个机制可直接移植，但递归没做、分数持平撑不出 EdgeBench、Performance 点选在测试集上、全篇零方差——值得关注的工程报告，不是 foundation。

### ZGCM-1
- **Title**: ZGCM-1: A Fully Open and Extremely Efficient Foundation Model for Math and Agentic Search
- **Institutes**: Zhongguancun Academy, Zhongguancun Institute of Artificial Intelligence
- **Source**: [link](https://arxiv.org/abs/2609.13356)  🔥 HF Trending ⬆️ 255   **📒 论文笔记**: [[2609-ZGCM1]]
- **核心**: 7.39B dense 基座的全栈技术报告，4.19T 预训练 + 600.51B mid-training token，靠 27 层 gated SWA（128 窗口）+ 5 层 global 的 5:1 混合注意力和 FP8 Muon 把上下文推到 256K。论点是小模型记不住开放网络，但可以用 long-CoT + tool use 把容量瓶颈转移到检索侧。数学侧同尺度确实领先（MATH-500 97.13、HMMT 2025 70.42、AIME 2026 75.00），agentic 侧最抓眼的是 BrowseComp 19.43% 对 Qwen3-235B-A22B 的 2.30%。真正稀缺的交付物是各阶段权重、中间 checkpoint、per-stage 数据与 recipe、W&B 日志，外加 8 条含负面结果的 finding。
- **锐评**: 先说好的：这是 OLMo 一脉里少见的诚实报告。Finding 1（lexical complexity 对 code/math 是烂难度代理）、Finding 5（long-CoT 过量伤指令遵循）、Finding 6（纯 agent 数据微调降交互保真度）都是别人能直接省钱的知识，信息量高过任何一行分数；KV cache 那组对比还是 iso-parameter 三方比较（7.39B full attention / 7.47B GDN 3:1 / hybrid），比只跟 full attention 比要讲究。BrowseComp 19.43 vs 2.30 是全文唯一真正支撑 thesis 的数据点——AIME/HMMT 领先只说明数学配比调得好，跟"检索替代参数记忆"没关系。
  现在说站不住的。标题里的 "Extremely efficient" 是吞吐口径冒充成本口径：4.19T + 600.51B token 不是小预算，而全文没有一个 GPU-hours、wall-clock、总 FLOPs 或金额数字（笔记 C6 确认是全文缺失，含附录 Table 6），在这个前提下写 "tractable on academic compute budgets" 就是空头支票。那个头条的约 4.2 倍更是纸糊的：1.4 × 1.5 × 1.8 × 1.1 四因子连乘的估计，对照基线（OLMo 3-style BF16/AdamW）根本没跑，Pre-LN 的 1.1 倍原文自己标 estimated/exploratory，而连乘隐含的"四项收益互不重叠"——SWA 的吞吐增益和 FP8 的系统增益明明作用在同一个 attention/GEMM 栈上——既没论证也没测量。顺带，3.94 倍只在 256K 成立，主预训练跑在 16K，对应增益是 1.4 倍。"14 个 reasoning benchmark 平均第一"同样是切片：完整套件 20 个，被砍掉的 6 个恰好装着 MMLU（落后 11.5）、GPQA-Diamond（落后 12.2）、IFEval（落后 12.8）——挑得这么准，很难说是巧合。Table 3 除 WebDancer 外全是抄各家公开报告、非同 harness 重跑，所以"与大一个数量级模型竞争"只在 WebDancer 和自建 BFS 两处成立，而 BFS 是自家 50 题子集，62% = 31/50，跟 Kimi-K2 并列、跟 GLM-5.1 差 2 题，全在噪声里。
  最刺眼的一条：标题打 agentic，SWE-bench Verified Mini50 只有 4.0%（2/50）、Terminal-Bench 2.0 只有 2.25%（2/89），两个数字都只躺在附录 Section 11.3/11.4 的 harness 描述末句，归属还写成含糊的 "ZGCM-family" 而非具体 checkpoint。SFT 里塞了 6 万条 software-engineering 轨迹换来 2/50——这才是本文最有价值的负面结果，却被埋在脚注位置。把 19.43% 和 4.0% 并排看，边界很清楚：检索能补知识缺口，补不了长程状态管理与执行可靠性。另外主表全部来自 256K SFT checkpoint，GRPO 的数据/reward/超参写了整节却没有任何 post-RL 结果表，RL 至今是纯 recipe 披露。最后，"Fully open" 这个词配上 GLM-5.1 tokenizer + GLM-5.1 conversation format + GLM tool-call/reasoning parser 的依赖链，以及全文对权重/数据/代码零 license 声明，只能读作"披露充分"，不是"可自由使用"。Finding 8 那 99 条自治性评级来自自家 9 位核心贡献者打分，当团队复盘可以，当 AI agent 能力边界的证据不行。
- **Rating**: `2` 👀 ，开放度与负面 finding 值钱、BrowseComp 那组对照是干净证据，但头条效率数字是连乘估计、benchmark 是挑过的切片、agentic 覆盖面远窄于叙事——值得看 recipe，别信封面。
