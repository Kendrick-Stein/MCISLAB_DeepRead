# 🔪 今日总结

**有，而且已经形成三个分工明确的类型**：把 CLI harness 本身当自变量测（HarnessEvolution 钉死模型只换 Qwen Code 的 35 个 release；WeaveBench 把同一 GUI plugin 移植到 OpenClaw / Codex CLI / Claude Code / Hermes 四个 runtime 做 2×4 sweep）、固定中立 harness 横评模型（WeaveBench 用 OpenClaw 作 reference runtime）、以及把 Codex/Claude Code 拉去做非编码任务（Agents' Last Exam 用 GUI-as-Tool 把 CLI harness 扩成 GCUA，TACTILE 在 macOSWorld 上横评四个 CLI agent）。

**web task 能做，但没人在标准 web benchmark 上认真测过。** 本次检索范围内没有把 Claude Code / Codex 直接跑在 WebArena / VisualWebArena / WebVoyager 上的受控研究——现有路径都是「CLI agent + GUI-as-Tool / browser MCP」而非原生 web agent。唯一 matched 的模态对照 GUI-vs-CLI 给出反直觉结果：最强 screen-only GUI（59.1%）高于最强 original-skill CLI（48.2%），补齐 skill 后 CLI 才反超到 69.3%——瓶颈是 skill 接口覆盖（原始只覆盖 37.6% 的 verifier checkpoint），不是 CLI 模态本身更强。

**评质量这件事，vault 里的证据几乎全是负面的：现在通行的评法都在系统性说谎。** outcome-only judge 高估 10–20pp，vanilla LLM judge 漏 44% safety violation，15.3% 的 FAIL 判定本身就是错的，同源模型当 verifier 错放率约 90%。可用的做法只有五条硬约束（见下文第 3 节），核心是 trajectory-level 取证 + Pass^k + 算力配平 + 记录 harness 版本。

## 1. 用 Claude Code / Codex 当 harness 的测试：三个类型

### 类型 A — harness 本身是自变量（模型钉死）

| 工作 | 设计 | 关键数字 |
|:--|:--|:--|
| [[Papers/2607-HarnessEvolution]] | Qwen Code CLI 的 35 个连续 release，模型钉死为自托管 Qwen3-Next-80B（vLLM），50 道 SWE-bench Verified × 2 run = 3500 次执行 | resolve rate **无显著趋势**（ρ=0.208, p=0.231，均值 30.5%）；token **单调上升**（ρ=0.743, p<0.0001，391K → 668K，+70%） |
| [[Papers/2607-ProgressiveDisclosure]] | 3 harness（Codex / Pi / Claude-Code）× 3 模型，固定任务指令、分块集合、verifier，只改文件系统侧的路由方式 | Codex 上 progressive disclosure **收益归零**（三子集全在误差内）；Claude-Code/haiku En.MC 0.7448 → 0.8667 |
| LoopsBench（`2608.00267`，Microsoft）| 112 个任务组织成依赖 DAG，flow-aware runtime 沿 ready frontier 放测试，已完成节点保留为回归义务 | 最强配置 **Opus-4.7 + Claude Code + outer continuation = 25.00%**；记录的 plan 只恢复了部分真实前置 DAG，回归事件在所有 loop profile 上都可见 |
| LoopArena（`2608.28281`，本次新发现）| Controller / Worker 分离：被评模型只当 Controller，每轮收结构化摘要后指挥一个**固定的** coding agent | 三档设置按执行范围与成本分层（Type I 不跑 Worker / Type II 跑任务切片 / Type III 跑完整任务）；abstract 只露出 "best observed Strict Success Rat…"，具体数字待核 |

HarnessEvolution 的方法论结论直接适用于任何要做这类实验的人：**现有 benchmark 报告普遍只记录模型版本、不记录 harness 版本，而多数 CLI 默认自动更新**——这让跨论文数字根本不可比。它的效率信号（token +70%）比效果信号可信，因为 50 任务上 per-release resolve rate 的抽样标准差约 4.6–6.5pp，观测到的 16pp 跨度与纯二项噪声同量级。

### 类型 B — harness 固定，横评模型

[[Papers/2606-WeaveBench]] 是目前这条线最干净的：真实 Ubuntu Desktop、114 个长 horizon 任务、8 个工作领域。它做了**两套 sweep**，必须分开读——

**B-1. Model-API sweep（Table 2）**：runtime 固定为 **OpenClaw**（作者明说选开源 OpenClaw 是 for fairness，即中立第三方），共享 tool pool / timeout / temperature / turn budget，每个 backbone 取最优 thinking。

| 模型（均在 OpenClaw 上） | PassRate |
|:--|:--|
| Claude Opus 4.7 | 35.1% |
| GPT-5.5 | 33.3% |
| GPT-5.4 | 22.8% |
| GPT-5.3-codex | 18.4% |
| GPT-5.2-codex | 6.1% |
| GPT-5.1-codex | 1.8% |

**两个 frontier 模型只差 1.8pp。**记住这个数，它是下面那张表的对照基准。

**B-2. Harness sweep（Table 3）**：GUI plugin 原样通过 thin adapter 移植到四个 runtime host，两个模型均 high thinking。这其实是**类型 A 的最强证据**，因为 harness 在这里是自变量。

| Backbone | Codex CLI | OpenClaw | Hermes Agent | Claude Code | 跨 harness 摆幅 |
|:--|--:|--:|--:|--:|--:|
| GPT-5.5 | **35.1** | 33.3 | 31.6 | **14.9** | −20.2pp |
| Claude Opus 4.7 | **13.2** | 35.1 | 28.1 | **41.2** | −28.0pp |

三条读法：

1. **交叉交互是双向对称的**：同厂配对最优（Opus+Claude Code 41.2、GPT-5.5+Codex CLI 35.1），跨厂配对最差（Opus+Codex CLI 13.2、GPT-5.5+Claude Code 14.9）。两个方向都成立，所以不能用"某个 harness 更好"解释。论文原话："cross-pairing the models with less aligned runtimes causes sharp drops"，归因于 "tool schemas, prompting conventions, and action-loop design interact strongly with model-specific tool-use behavior"。
2. **harness 的效应量比模型大一个数量级**：固定中立 harness 时模型间差 1.8pp，换 harness 让同一模型摆动 20–28pp。**任何不报告 runtime 的 CUA 分数都不可比**——这跟 [[Papers/2607-HarnessEvolution]] 「benchmark 报告只记模型版本不记 harness 版本」的结论从两个方向指向同一件事。
3. **中立第三方 runtime 两边都不塌**：OpenClaw 33.3/35.1、Hermes 31.6/28.1，均接近各自上限。塌陷只发生在跨厂配对，所以这是 harness–model **适配**问题，不是闭源生态锁定。

另需注意 PassRate 与 Overall 会**排序反转**：Opus+Hermes 的 PassRate 更低（28.1 vs 35.1）但 Overall 更高（0.516 vs 0.482）。单指标结论在这个量级上不稳。

## 2. Web task：能做，但证据链有个洞

**直接的空白**：在本次检索范围内（arXiv API 四轮查询 + vault 全文 grep），**没有**把 Claude Code / Codex 跑在 WebArena / VisualWebArena / WebVoyager 上的受控研究。WebSearch 在本环境持续返回 API 错误（`output_config.effort 'xhigh' is not supported`，与 [[Topics/Harness-Component-Attribution]] 调研日志记录的是同一个环境级故障），所以这条「未发现」应读作**当前检索范围内未发现**，不是「无人研究」。

能拿来回答的最强证据是 [[Papers/2606-GUIvsCLI]]——文献中唯一 matched 的模态对照，440 个桌面任务 × 18 应用，同目标、同初态、**同一个 executable verifier**，两侧各自只许用 modality-native 动作：

| 条件 | 最强模型 | Full pass | 平均时间 |
|:--|:--|:--|:--|
| GUI（screen-only） | GPT-5.4 | **59.1%** | 455.8s |
| CLI（original skills） | Codex GPT-5.5 | 48.2% | 188.1s |
| CLI（patched skills） | Codex GPT-5.5 | **69.3%** | 162.6s |

三个可以直接用的结论：

1. **「换成 CLI 就更强」是错的**——受控对照下 screen-only GUI 反而高 10.9pp。
2. **CLI 的瓶颈是接口覆盖不是执行能力**——原始 skill 只能稳定产生 37.6% 的 verifier 可读目标状态，补齐后 CLI 才反超 21.1pp 且快 2.8 倍。
3. **patched 那个 69.3% 不能当泛化能力读**——作者自己警告修复过程用了 verifier 信息，这是 verifier-observed coverage completion。

配套的安全侧证据来自 `2606.05233`（793 episodes / 24 个 multi-step web 任务 / 56 个攻击模板）：对 Claude Sonnet 4.6 与 GPT-5.4 测得 **0/140 multi-step 攻击成功**（Clopper-Pearson 95% 上界 2.60%），但**同一份权重在 coding-agent benchmark 上被手写 skill injection 打到 100%**。作者的结论是 frontier safety hardening 是 **domain-conditioned** 的，只针对被反复攻击的 browser surface。这对本问题的实践含义很直接：**让 Claude Code 去干 web 活，等于把任务放在它没有被针对性加固的那一侧**。

实践路径上，目前可行的三种接法各有代价：GUI-as-Tool（ALE 路线，能跑但难任务 0%）、MCP execution substrate（TACTILE 路线，+9pp 但增益集中在 AX 可用的任务）、CLI skill 层（GUI-vs-CLI 路线，快但受 skill 覆盖率上限约束）。[[Topics/AgentHarness-Design]] 第 1 节按接口层级把这五种做法的前置条件与已测得代价整理成了表。

## 3. 怎么评估完成质量：五条硬约束

这是 vault 里证据最厚的一块，而且结论几乎全是负面的——**现在通行的评法都在系统性说谎**。

### 3.1 outcome-only judge 不可用

- [[Papers/2606-WeaveBench]]：trajectory-aware judge 发现 outcome-only grading **系统性高估 10.3–20.2pp**（GPT-5.5 从 53.5% 降到 33.3%），且论文明说这是**下限**——因为每个 rollout 都已经收到 anti-fabrication prompt。35.2% 的失败源于 reward hacking 而非能力不足，视觉 grounding 失败 <4%。
- [[Papers/2604-ClawEval]]：vanilla LLM judge **即便拿到完整 transcript + grader 源码**，仍漏 44% safety violation、13% robustness failure。确定性检查是必需品不是 nice-to-have。

### 3.2 Pass@k 掩盖可部署度，要报 Pass^k

[[Papers/2604-ClawEval]]：error injection 让 Pass@3 几乎不动，却把 **Pass^3 砍掉 24pp**。14 个 frontier 模型跑 300 任务，最强的 Claude Opus 4.6 overall Pass^3 只有 70.4%。Pass@3 与 Pass^3 之间的 gap 才是真正的可部署度。

### 3.3 FAIL 判定自己就有 15% 噪声

[[Papers/2607-MisScoreCUA]]：审计 5 个 CUA benchmark 的 150 条 zero-reward 轨迹，**15.3% 的 FAIL 判定是错的**（10.7% evaluator false negative + 4.7% 任务本身坏掉）。推论很硬：**排行榜上个位数的差距没有意义**。剩下 122 条真失败里，verification/feedback 类占 39.3%（其中 feedback-blind no-op 单类 29.5%）、planning 类 35.2%，而 execution/grounding 只有 13.9%。

### 3.4 别拿同源模型当 verifier——独立性是有剂量的

[[Topics/Harness-Component-Attribution]] 把这条整理成了剂量阶梯：

| 独立性剂量 | 实现方式 | 实测判决质量 |
|:--|:--|:--|
| 低 | 同 backbone、仅 context 不同 | [[Papers/2607-StateAct]] finish gate 在 76 个 non-perfect 任务上**错误放过 68 个（≈90%）**；[[Papers/2605-TeamBench]] 池化 false-accept **49.4%** 对 false-reject 6.6%，且随模型从 36.3% 到 77.0% 跨越一倍 |
| 中 | 异族模型 | [[Papers/2607-HarnessBank]]：evolver 用 Claude Opus 4.8、task agent 用 Qwen3.6-27B；未报 false-accept/reject |
| 高 | 确定性检查 / 执行结果 / 统计判据 | [[Papers/2605-GRASP]] 留出探针集净修复计数；[[Papers/2606-SkillNb]] 执行式 gate；HarnessBank 配对 t 统计量 z ≥ 1.96 |

理论侧有对应边界：[[Papers/2606-CodeSelfReviewCollapse]] Theorem 2.3——门控信号来自模型自身时，被门控的分布退化为未门控分布，通过率上升而正确率下降。

### 3.5 必须做算力配平，否则测的是预算不是方法

- [[Papers/2605-GRASP]] 是文献中唯一提供 compute-matched control 的：去掉验收闸门 88.8% → 63.5%（K=4），但**算力配平对照（花同样验证预算却丢弃验证结论）塌回 67–71%**——也就是说大部分「验证收益」其实是算力收益。
- [[Papers/2606-SkillMemoryBudget]]：补上 token-matched vanilla 臂后，memory/skill 库的增益被追平或反超；还查出 AWM 有 49.5–52.3% 的 workflow 来自失败轨迹。
- [[Papers/2607-ProgressiveDisclosure]] 的反例：K=20 时 raw 花 68.3M token/问题（约 \$52）拿最差准确率，flat 用一半 token（\$25）拿近两倍准确率——更准更省被当作两个并列观察报告，而非受控结果。

### 3.6 补一条：按基线质量分层，别报平均值

[[Topics/Harness-Component-Attribution]] 的核心结论——**harness 组件的收益与基线轨迹质量负相关，在原本已成功的轨迹上普遍为负**。三条独立证据链：TeamBench 按 Solo 分数五分位分层（Q1 +15.7，Q3–Q5 团队**落后** 6.8–10.1，全局平均只 +0.5, p=0.20）；LongHorizon-Harness 自身数据同形（基线 ≤0.04 的 6 个任务全回到 0.30–0.92，而基线已达 83.3 的 Desktop 域 mean score **反降** 0.8671→0.8465）；ProgressiveDisclosure 的 harness 交互。

**据此可提出的可证伪论断**：目前没有任何受控证据显示独立验证提升了能力上限；所有被测出的验证收益都是「避免回归 / 抬失败地板」形态。

### 3.7 想直接抄的最小方案

如果你要给「Claude Code 干完的活质量如何」搭一套评测，按上面的证据，最小可信配置是：

1. **判据优先确定性**——filesystem / service / permission state 的执行式检查（`2608.30207` 的 SIR 就用全确定性 oracle 而非 LLM judge），LLM judge 只用于确定性检查覆盖不到的部分，且必须看 trajectory 不能只看 output。
2. **报 Pass^k 而非 Pass@k**，并同时做扰动注入。
3. **verifier 与 executor 异族**，且报告 verifier 自身的 false-accept / false-reject 率——这一步几乎所有 harness 论文都跳过了。
4. **对照臂算力配平**，GRASP 式「花同样预算但丢弃结论」是分离「验证行为」与「验证结论」的决定性设计。
5. **记录并 pin 死 harness 版本**，按基线分数分位分层报增益。

第 6 条如果 loop 与 agent 都在变，用 LoopArena 的 Controller/Worker 分离——固定 Worker 只评 Controller，这是目前唯一把「功劳归 loop 还是归 agent」形式化了的设计。

### LoopArena
- **Title**: LoopArena: Benchmarking Models as Runtime Controllers for Loop Engineering
- **Institutes**: 未核（abstract 未列）
- **Source**: [link](https://arxiv.org/abs/2608.28281) 📰 HF Daily ⬆️ 89   **📒 论文笔记**: 未生成（已入队）
- **核心**: Loop Engineering——围绕 coding agent 组织开发工作、由 loop 决定监控什么/派什么活/跑什么检查/何时停。问题在于一次端到端 run 的最终结果说不清成功是 loop 指挥得好还是 coding agent 本身能干。LoopArena 把被评模型固定为 Controller，每轮收结构化摘要后指挥一个**固定的** Worker，三档设置按执行范围与成本分层：Type I 不跑 Worker、只用 execution-validated 问题评 Loop Contract 选择；Type II 在任务切片上重复控制；Type III 跑完整任务。
- **锐评**: 这个 formulation 是对的，而且是本次检索里唯一把「归因」而不是「分数」当一等公民的。固定 Worker 换 Controller 就是把 [[Papers/2607-HarnessEvolution]] 那套「钉死模型只变 harness」的思路补上了另一半——后者证明了 harness 版本能主导数字却做不了组件归因，LoopArena 至少把 loop 这一层单独拎出来了。Type I 不跑 Worker 就能打分这个设计很聪明，成本低到能当日常回归用。**但 abstract 里 "the best observed Strict Success Rat…" 被截断，主结果数字未知**；而且固定 Worker 意味着结论天然绑定那一个 Worker——如果换成能力更强的 Worker，Controller 的边际价值会不会像 [[Topics/Harness-Component-Attribution]] 里反复出现的那样塌成零甚至为负，abstract 没交代。这正是该文献族最常见的漏项。
- **Rating**: `3` 🔥，正面命中「怎么把 loop 与 agent 的功劳分开」这个本次最核心的方法论缺口。

- **核心**: 把 agent harness（memory 管理、planning 策略、action protocol、tool/skill 编排）形式化成一个受固定四模块协议约束的、可组合可机器生成的 artifact，训一个 JIT-Agent 模型为任意现成 agentic LLM 即时合成任务自适应的 harness，并能修复 harness、从历史配置档案里蒸馏性能信号做自演化。DeepSeek-V4-Flash 装上后在 DeepSearchQA 超过 GPT-5.6（+9.1）、OdysseyBench +4.3，已经很强的 GLM-5.2 还能 +20.2；作者称生成的 harness 与 OpenCode、Claude Code 这类成熟 runtime **性能相当**。
- **锐评**: 「harness intelligence 是可训练的」这个 framing 立得住，而且拿 Claude Code 当对照而不是当基建，正好是本次问题要的那种工作。但三处要盯：其一，**「与 Claude Code 相当」是最关键的一句却最含糊**——相当在哪个 benchmark、哪个模型、什么算力口径？[[Papers/2606-WeaveBench]] 已经证明 model×runtime 是强交互项，同一个 Opus 4.7 换个 runtime 就从 41.2% 掉到 13.2%，泛泛说「competitive」没有信息量。其二，+20.2 这种量级在 harness 文献里几乎必然伴随 token 暴涨，而 [[Papers/2607-HarnessEvolution]] 测出 harness 迭代的真实效应恰恰是「成本涨 70%、效果不动」——abstract 只字未提 token。其三，「固定四模块协议」既是卖点也是天花板：能生成的 harness 空间被协议先验框死了，这跟 [[Papers/2608-StrongToWeakHarness]] 那种「scaffold 空间不受限、出现什么技术本身就是因变量」的做法是相反的取舍，而后者的自动 scaffold 最好成绩（0.912）仍输给人工（0.939）。
- **Rating**: `2` 👀，问题选得准、卖点直指本次核心，但 abstract 里最该量化的两件事（对 Claude Code 的对照口径、token 成本）都没量化。

### Agentic Artifact Creation
- **Title**: Agentic Artifact Creation: Systems, Evaluation, Principles, and Opportunities
- **Institutes**: 未核（abstract 未列）
- **Source**: [link](https://arxiv.org/abs/2608.28122) 📰 HF Daily ⬆️ 52   **📒 论文笔记**: 未生成（已入队）
- **核心**: 综述 259 篇（截至 2026-08-20），其中 230 个系统 + 29 个 benchmark。定义 agentic artifact creation 为「AI 实质性构建或修订一个交付物、且中间观察会改变后续工作」的 stateful construction，功能上把 artifact 的可操作表示、construction policy、runtime verification 三者串起来。横向比六个 artifact 家族，把应用场景与评测实践当作两个独立维度分析。
- **锐评**: 综述本身不产生新证据，但它抛出的两句话值得单独拎出来：「分解能降低局部复杂度，但同时抬高协调与重组成本」——这跟 [[Papers/2608-LongHorizonHarness]] 把 executor 每轮 fresh context 化的做法是同一个 trade-off 的两面，而后者从未测过重组成本；「learned judge 在与 generator 共享偏好或盲点时可能提供不了多少独立证据」——这就是 [[Papers/2606-CodeSelfReviewCollapse]] Theorem 2.3 的自然语言版，一篇综述能自发收敛到同一结论，说明这条约束已经是领域共识而非个别发现。价值在于 29 个 benchmark 的评测实践横评，正好补本次问题第三问的地图。风险是综述的老毛病：定义宽到把六个家族硬塞进一个框架，跨家族的「原则」很容易退化成放之四海皆准的废话。
- **Rating**: `2` 👀，当评测实践的索引用，不当结论用。

### Knowledge-Gated Tasks
- **Title**: Ignorance or Incompetence? Constructing Knowledge-Gated, Verifiable Tasks for LLM Agents
- **Institutes**: DatagridsAI（据 repo 链接推断，待核）
- **Source**: [link](http://arxiv.org/abs/2608.30322v1) 📄 arXiv   **📒 论文笔记**: 未生成（已入队）
- **核心**: 提出知识门控的任务构造协议：把任务指令与一个装着私有约定、参考表、工具算子的紧凑 artefact 分开，两个条件（给 artefact / 不给）下任务指令**逐字节相同**，再配上构造期 provenance、泄漏审计与可执行 witness，让「对 artefact 的依赖」显式且可测。15 个校准任务上，某个 frontier agent 配置**给 artefact 时 68.0% 通过、不给时 0%**；有一个任务给了看似合理但错误的 artefact 同样 5 次全 0。
- **锐评**: 68.0% vs 0% 这个对照干净得少见——byte-identical instruction 这个约束把「任务变难了」和「知识被拿走了」彻底分开，是本次看到的所有工作里唯一在**任务构造层**做到严格控制的。「plausible but incorrect artefact 也 0%」这条更狠：说明 agent 不是在瞎猜，是真的在用 artefact，顺便排除了「靠通用先验蒙对」的解释。对本次问题的用处在于，评 Claude Code 干专业活的质量时，最容易犯的错就是分不清它是不会做还是不知道你们公司的约定——这套协议给出了可执行的分离办法。**但作者自己划的边界要照抄**：15 个校准任务经过五次试验的经验筛选只留下 7 个，且论文明说这些实验只验证了构造协议的行为、**不证明保留下来的任务能改善 post-training**。规模也小到不能当 benchmark 用，只能当协议模板。
- **Rating**: `2` 👀，方法论价值远高于实验规模，正好补「怎么构造让分数有意义的任务」这一环。

### EvoUndo
- **Title**: EvoUndo: Recoverability-Constrained Self-Evolution for LLM Agent Harnesses
- **Institutes**: 未核（abstract 未列）
- **Source**: [link](https://arxiv.org/abs/2608.28363) 📰 HF Daily ⬆️ 5   **📒 论文笔记**: 未生成（已入队）
- **核心**: agent 在运行时改自己的 prompt、工具、middleware、资源与执行 harness，一次成功的 mutation 可能留下在**别的状态下无法安全回滚**的持久影响。EvoUndo 做的是跨反事实状态地表示、合成、诊断与独立验证这类自修改的可恢复性。600 个未见过的 one-shot 自演化任务里挑出 197 个「能力提升但可恢复性验证不过」的 mutation：原始恢复表示下常规修复策略恢复 **0/197**；确定性 oracle 在原恢复语言 L0 下恢复 48/197，扩展恢复演算后到 191/197。2×2 protocol-locked 干预把瓶颈拆成两个——精确状态地址 grounding 让 0/48 升到 38/48（79.2%），扩展恢复语言在 S1 层让 142/143（99.3%）可恢复。
- **锐评**: 0/197 这个数字本身就值回票价——它说明「让 agent 自己改自己的 harness 然后出问题了再改回来」这个所有人默认成立的假设是**彻底不成立**的。2×2 把「地址不够精确」和「语言表达力不够」分离开，是本次看到的少数几个做了真消融的工作。对本次问题的相关性是间接但要紧的：Claude Code 的 CLAUDE.md / hook / skill 都是运行时可改的控制面，[[Papers/2608-StateM]] 已经点出「YAML 可编辑本身不提供安全边界」，EvoUndo 给的是这句话的定量版。**保留意见**：600 个任务是 one-shot 合成的，跟真实 harness 演化（[[Papers/2607-HarnessEvolution]] 里 Qwen Code 那种每天 2 次以上的人类 PR 流）不是一回事；而且 191/197 是 **oracle 分析**的上界，不是任何实际系统达到的——真跑的 gpt-oss-120b 在最优配置下还掉到 133/143（93.0%），abstract 里这个「加了精确地址诊断反而变差」的反直觉结果没解释。
- **Rating**: `2` 👀，把一个被普遍默认的假设证伪，且做了真消融；但 oracle 上界与实测之间的差距需要读正文。

### GenRubric
- **Title**: GenRubric: Self-Evolving Rubric Generation for Scalable LLM Evaluation
- **Institutes**: 未核（abstract 未列）
- **Source**: [link](http://arxiv.org/abs/2608.29856v1) 📄 arXiv   **📒 论文笔记**: 未生成（已入队）
- **核心**: LLM judge 常在打分时才现场推导 query-specific 标准，导致评测要求欠定、覆盖难审计。GenRubric 用 rubric-induced self-consistency 做自演化：同一 query 独立采样出的多份 rubric 各是其潜在评测要求的局部视图，好的 rubric 应当诱导出能跨这些互补视图泛化的回答。用 RL 实现，结合跨 rubric 的 comprehensiveness 信号与 group-level / criterion-level 的 rubric 质量奖励，训了 4B/8B/14B 三个尺度。
- **锐评**: rubric-induced self-consistency 这个信号设计有意思——用「rubric 诱导的回答能否跨视图泛化」来代替人工标注，绕开了标注成本。但对本次问题基本用不上，而且踩在一条已知的雷上：**self-consistency 是同源信号**，[[Papers/2606-CodeSelfReviewCollapse]] Theorem 2.3 说的就是这种情况下门控退化为不门控。abstract 里的验证是「生成 rubric 诱导的评测与专家 rubric 诱导的评测之间的一致性提升」——一致性提升不等于判决正确率提升，[[Papers/2605-TeamBench]] 那三个 LLM judge 在看得到确定性判决时 Fleiss κ=0.74、看不到时降到 0.07，作者据此声明二者都不能当独立 grader 验证。同样的怀疑适用于这里。更根本的问题是，agent 轨迹的判定难点不在「标准写得全不全」，而在 [[Papers/2604-ClawEval]] 测出的那 44% ——judge 拿到全部信息仍看不出违规。rubric 再全也补不上这个洞。
- **Rating**: `1` 💤，对通用 LLM 评测可能有用，对 agent 轨迹质量判定用处有限。
