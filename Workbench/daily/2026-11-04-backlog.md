### VeriCUA
- **Title**: VeriCUA: Learning Proactive Verification for Reliable GUI Agent Rewards
- **Institutes**: Southwest Jiaotong University, Tsinghua University, University of Electronic Science and Technology of China, National University of Singapore, Renmin University of China, Peng Cheng Laboratory
- **Source**: [link](https://arxiv.org/abs/2610.26469)  📄 arXiv   **📒 论文笔记**: [[2610-VeriCUA]]
- **核心**: proactive GUI verifier 可以拆成两部分，一个可训练的 Judge 负责写 check、决定什么时候停，一个冻结的只读 Probe 去 Actor 的终态环境里取证。Actor 终态无法复现，没法在同一状态上采一组 verifier rollout，所以作者用 REINFORCE++ 在 batch 内跨终态归一化，reward 里加一项 Probe 使用惩罚（判对时，不调 Probe 得 +1.0，调了 Probe 得 +0.7），让 Judge 学会只在截图不足以判断时才去 probe。只在 OSWorld 上训练的 4B Judge 三个环境 macro agreement 为 74.08，few-shot GPT-5.4 为 68.72，Probe token 少 47.6%–59.8%。1B 版本 71.62，超过所有 prompted Judge。拿它当 reward 做 GRPO，Qwen3-VL-4B Actor 的 Pass@4 从 43.93 升到 47.14。
- **锐评**:
  - 好的地方：问题定义抓得准。"终态只能验证一次"把 GUI verifier 和数学、代码 verifier 区分开了，那两类可以复制问题、多次采样验证。解法也朴素：不做 environment forking，不用 value model。对照设计干净，prompted 和 trained 版本共享 backbone、Probe、prompt 和预算，所以 4.50 / 8.62 / 21.11 点的提升可以算到学到的策略头上。Table 4 把 Probe 从 35B-A3B 换到 4B，agreement 是 82.00 / 82.73 / 82.07，基本不动，这支持"能力在 Judge 里，不在 Probe 里"。最有信息量的数字是下游 RL 里 failed Probe dispatch 从 16.6% 降到 3.2%：prompted Judge 有相当一部分失败是发出了 Probe 执行不了的检查，问题出在接口这一层，不在推理能力。
  - "strategy 胜过 scale"在主场站不住：OSWorld 上 VeriCUA-4B 只比 zero-shot GPT-5.4 高 0.12 点（82.00 vs 81.88），macro 优势主要来自 MobileWorld 的 +11.25。MobileWorld 换了另一个 Probe（GUI-Owl-1.5-32B），所以这 11 点有可能只是 GPT-5.4 写的 check 和这个 Probe 的接口对不上。更准确的结论是"prompted 大模型不会给这个特定的冻结 Probe 写可执行的 check"，和"scale 没用"差得很远。
  - 标题说 learning，但大头是蒸馏：OSWorld 上 prompted 73.73，SFT（约 1,270 条 Kimi-K2.6 trace）后 79.41，online RL 后 82.00。SFT 贡献 +5.68，RL 只有 +2.59。teacher Kimi-K2.6 自己的 prompted macro 才 69.62，学生超过老师主要靠 rejection sampling 筛出判决正确的 trace。这个机制本身成立，但卖点应该落在"筛过的 trace 加 SFT"上，RL 只是锦上添花。
  - 评测集只留确定性终态：6 次 re-execution 结果一致、末帧 pHash > 0.95 的轨迹才保留，single-attempt 约束最难处理的不稳定终态全被剔掉了。Table 1 没有 CI，MobileWorld 和 WebArena-V 各 100 条，WebArena-V 上 trained 比 prompted 只高 1.25 点，大约每次 run 多判对 1 条，落在噪声里。OSWorld 训练用 280 个任务、评测用 414 条轨迹，论文只说轨迹 disjoint，任务层面有没有重叠没交代，Actor 池也部分重合，所以 OSWorld 上的 82.00 不能当泛化结果看。
  - reward 安全性只讲了一半：Table 1 只报 agreement，没把 false positive 和 false negative 拆开。下游 RL 里报了 FN 从 10.0% 降到 4.6%，但对 reward hacking 威胁更大的是 FP，这个没有单独分析。OSReward 已经指出 judge 普遍偏宽松，这一项不测，"reliable reward"的说法就缺一块。
  - 下游收益很薄：OOD 从 17.57 到 22.97，在 74 个任务上大约多解出 4 个。trained 和 prompted VeriCUA 在 OOD 上差约 2 个任务，Table 2 只有单次训练，没有 seed 方差。All 指标上 trained 版本是 47.14，ZeroGUI 是 45.36，差 1.8 点，作为"更好的 reward 带来更好的 Actor"，证据偏弱。
  - 成本口径对自己有利：只计 Probe token，Judge token 不算。1B–4B Judge 这样算问题不大，但所谓 Pareto frontier 只是 Probe 成本这一个维度上的。
  - few-shot 对照有混杂：OSWorld 的 few-shot 示例之一就是 Fig 1 里那个"给 slide 加 notes"的任务，few-shot 设置又只给格式不给证据，不能当 prompt 工程的上限看。
- **Rating**: `2` 👀，"Judge 学写 Probe 执行得了的 check，再配 single-attempt reward"这个设计值得借鉴，dispatch 失败率这个诊断也有价值；但 OSWorld 上对 GPT-5.4 几乎没有优势，增益主要来自 SFT 蒸馏，评测剔除了不稳定终态，也没拆出 FP，离 Foundation 还差一截。

### AndroidFlux
- **Title**: AndroidFlux: Evaluating Failure Recovery and Recovery Action Reward Modeling in Mobile-Use Multimodal Agents
- **Institutes**: Georgia Institute of Technology, Konkuk University
- **Source**: [link](https://arxiv.org/abs/2610.34384)  📄 arXiv   **📒 论文笔记**: [[2610-AndroidFlux]]
- **核心**: 作者把 AndroidWorld 上真实 policy 的失败轨迹回放（或用 emulator snapshot 恢复）到第一个可恢复错误附近的几个 checkpoint（$t{-}n$、$t$、$t{+}1^{\pm}$），再把同一个坏状态和重新渲染的历史交给不同 target agent 接着跑，并且不提示它"你需要恢复"。评测分两部分：HV 集 80 例、LV 集 312 例用来测 recovery；另用 12-agent panel 的下游成功数差构造 100 对 recovery-action 偏好，用来测 reward model。主要结果有四条。MobileRun 把 Gemini Flash 3.0 的 HV $t_{\text{all}}$ 从 27.5 提到 67.5。错误早时 rewind 更有用（+8.76pp），错误晚时 inject 更有用（+5.86pp），两者之差随错误位置变化 +12.22pp，95% CI [+4.1, +20.8]，18 个模型里 17 个方向一致。UI-Genie BT RM 在自家集合上有 0.90+，到 AndroidFlux 上只剩 0.49/0.52，接近随机。用 8.5k 条以失败为中心的上下文做 offline GRPO，clean 和 recovery 成功率同时上升。
- **锐评**:
  - 全文最硬的是 Table 4 的 rewind/inject 交叉。有 episode-level bootstrap、ICC 和 design effect（有效样本只有名义对数的 35-39%），sign test p=0.0001，这是整篇唯一经得起统计追问的发现，而且能直接用来设计 retry/rollback 策略。第二个能拿走的是 Table 5：UI-Genie RM 在自家集合上 0.904/0.915，换到 policy-induced 错误上 0.490/0.520，比不训练、直接用 MAI-UI-8B 的 action likelihood（0.600）还差。这说明"扰动正确轨迹造负例"训出的 RM 迁移不到真实错误分布。
  - 自相矛盾的地方在 offline RL。Table 5 刚说 UI-Genie BT-128K 在 recovery 偏好上接近随机，Table 6 的 GRPO reward 用的偏偏就是这个冻结的 BT-128K。结果是单 seed、65 个任务，最佳配比比 UI-only 在 clean 上高 +4.6pp，作者自报的 seed 噪声是 3.1 点；error-$t$ 高 +9.3pp，噪声是 6.1 点，只略高一点。一个近乎随机的 reward 也能带来"提升"，更可能是数据分布本身起了作用（$t$/$t{-}1$ 上下文占 60%），和 reward 关系不大。论文没有做随机 reward 或 SFT-only 对照，这一节的机制解释站不住。还有一个泄漏风险：训练语料的 10 个 agent 和 HV 的 source 有重叠（Qwen3-VL-2B/4B、MAI-UI-8B），论文也没说清 65 个评测任务是否全部落在被排除的 20 个任务类型里。
  - CoT 结论"有 GUI 领域 RL 的模型才受益"只建立在 2 个模型上。其中 GPT-5.6 Terra 是闭源模型，有没有做过 GUI reasoning RL 从论文里无法核实，Gemma-4 在 LV 集上也是正增益（+2.88）。这只是两个数据点的相关观察，写成"domain-aligned RL enhances error recovery"属于 overclaim。
  - Headline "recovery only partially correlates with clean-start" 全文没有给任何相关系数，只有 Table 9 里 GUI-Owl-1.5-32B 一个例子（AndroidWorld 66.38，$t_{\text{all}}$ 32.50），也没有把任务子集难度的影响和能力差异分开。
  - 规模和标签质量都偏弱。HV 只有 80 例，1 例就是 1.25pp。RM 集只有 100 对，一半恰好卡在 margin=2 的阈值上，12 个 agent 里差 2 次成功作为偏好标签噪声不小，单 scorer 之间 0.52 到 0.60 的差距基本在 CI 内。LV 的首错标注 recall 只有 50.8，"第一个错误"有相当比例其实不是第一个。$t{-}3$/$t{-}5$ 分别只有 60.0%/32.3% 能回放，其余混入了 clean start，$t_{\text{all}}$ 被稀释。
  - MobileRun 从 27.5 到 67.5 很亮眼，但它是多次调用、带 reflection 的 agentic framework，和单次调用的 VLM 比时没有控制推理预算，所以这个数字只说明"多想几轮有用"，不能当成能力对比。
  - 和 GUI-RobustEval、ReTrace 的本质区别有三点：mobile 场景、错误前/中/后三段 checkpoint、不提示恢复的跨 agent 接管，再加上用下游后果定义 RM 偏好。ReTrace 发现 post-trained 专用模型受益小，本文发现 GUI 专家更稳，两者结论有张力，但谁都没有做控制变量来解释原因（错误来源不同、是否提示恢复）。代码和数据仓库链接未找到。
- **Rating**: `2` 👀，rewind/inject 交叉和"合成负例 RM 不迁移"这两个发现值得借鉴，但 CoT 归因只有 2 个样本，offline RL 用近随机 RM 做 reward、单 seed 且增益在噪声量级，benchmark 规模也撑不起大部分模型间比较。

### RightClickWrongBox
- **Title**: Right Click, Wrong Box: Grading GUI Grounding by What a Click Does
- **Institutes**: Zhejiang University, Zhejiang Geely Holding Group
- **Source**: [link](https://arxiv.org/abs/2610.36831)  📄 arXiv   **📒 论文笔记**: [[2610-RightClickWrongBox]]
- **核心**: 现在的 GUI grounding 评测只认"点在标注框内"。可网页上同一个动作往往有好几个入口，比如重复链接、label 和它的 control、商品图和商品标题。作者把正确性改成"这一下点击产生的 outcome 是否和标注目标一致"，用一个浏览器 probe 逐点执行点击、给结果做 fingerprint，在 Gitea / Oscar 上建出 outcome map 和 execution judge。结果是 17.7% / 31.2% 的 live target 和自己的 box 对不上，三个 7-8B grounder 被 box 判错的点击里有 17.6-20.5%（Gitea）和 29.7-38.1%（Oscar）其实达成了目标 outcome。ScreenSpot-v2 上用人工盲审，web 等价率 14.4%，mobile / desktop 只有约 1%，修正幅度 0.2-1.8 点，和领域 head-to-head 差距的中位数 1.15 点是同一个量级。把等价点击计入 GRPO reward，在 3B 模型上没有稳定收益（四个测试集上均值差都在 0.25 点以内）。
- **锐评**:
  - 这篇的价值在于掀了 grounding 榜单的桌子，不在方法。把 seed 方差（至多 2.6 点，seed 42 和 seed 44 给出方向相反的显著结论，p=0.03 / p=0.02）、测试采样方差（bootstrap 半宽 1.26-1.54）、评分 bias 放在同一刻度上比较，再拿 58 个 head-to-head 里 21 个领先幅度不超过单 seed 效应、29 篇论文无一报告方差的统计收尾，对"+1 点 SOTA"的文化是正面打脸。预登记加 checksum、双人盲审 κ=0.95，这种实验纪律在 GUI 圈很少见。
  - live 证据只有两个自建 web 应用，主实验还用模板指令 `Click the <role> "<text>"`，这种格式本身就会让同文字副本变成合法答案。收益几乎全部集中在 193 条"同文字多副本"条目上（box 28.5-35.2% 对 outcome 90.7-100%），3,092 条唯一匹配条目上 outcome 准确率反而略低于 box。所以"约 1/5 被拒点击其实是对的"，更准确的说法是"重复链接很多"。自然语言改写后 Oscar 的修正涨到 6.2-8.4 点，但改写是 Qwen3-4B 看不到屏幕写的，抽读 100 条有 10 条明显不合格，这里有多少是改写制造的歧义，作者没有拆开。
  - ScreenSpot-v2 的 per-model 修正建在很薄的样本上：UI-Venus-1.5-8B 只有 20 个 audit unit、3 个 E，"差距从 2.9 缩到 1.7"就是从这里外推出来的。作者自己也承认，加入 audit 不确定性后 3 对排序翻转的区间都包含 0。这个数字适合当警示，不能当新榜单用。
  - "7-8B 的被拒点击里 20.6% 是等价，3B 只有 2.9%"大概率是选择效应：强模型框外错误少，剩下的自然多是点了另一个副本。这说明的是强模型错误分布的特点，推不出"box scoring 对强模型更不公平"。何况 7-8B 只有 3 个模型。
  - fingerprint 只取第一个匹配签名，non-GET 请求一律拦截，self-check 里已经出现三个不同 Delete 共用一个确认 dialog、被合并成同一 outcome 的误判。单步等价也不等于多步等价。
  - 训练端的负结果没有信息量：3B + LoRA + 396 updates，held-out 的多副本条目上 base 已经 92%、训练后 100%，天花板太低，根本检验不出 reward 的价值。作者也只说 "remains unshown"，没有 overclaim，这一点算诚实。和 GUI-Libra（partial verifiability 放在训练端修）的张力还没有被这个实验解决。
  - 和 MobiBench 的本质区别是：等价集合靠执行自动获得，不靠人工标 branch。但 Mind2Web 上只测出 1.3% 的静态等价，mobile 约 1%。这说明问题基本只存在于 web，"grounding 剩余错误是评分假象"的结论不能推广到全平台。
  - 正文写了 "We release"，但笔记里没有找到公开 URL。
- **Rating**: `2` 👀 ，把 bias 和 noise 拆开、外加报告方差的规范，是每个做 grounding eval 的人都该照做的；但 live 证据只来自两个自建站点和模板指令，ScreenSpot-v2 修正的样本太薄，训练端实验又撞上天花板，还不足以改变这个方向的做法。

### SA-CUA
- **Title**: Towards Safe Autonomy for Computer Use
- **Institutes**: Tübingen AI Center, University of Tübingen
- **Source**: [link](https://arxiv.org/abs/2610.18508)  📄 arXiv   **📒 论文笔记**: [[2610-SACUA]]
- **核心**: SA-CUA 是一个 dual-LLM 的 IFC 防御框架，防的是 CUA 的 indirect prompt injection。屏幕默认全部遮蔽，只把 AT-SPI accessibility tree 上按离线规则判为 trusted 的区域放给 planner。click 和 typing 不能落在 untrusted 区域。untrusted 值要进入 trusted 域，必须走 robust endorsement：由看不到候选值的组件从可信来源推出预期值，再做确定性比对。在 WASP†/RTC†/RTC-value 三个对抗 suite 上，SA-CUA 和 CaMeL-CUA 的 ASR 都是 0，SA-CUA 完成率高得多（Qwen3.8-27B 在 RTC† 上 86.2% 对 18.5%）。代价是无攻击时 OSWorld 子集从 58.3% 掉到 30.6–38.9%，token 成本是 unprotected CUA 的 4.2–7.5 倍。
- **锐评**:
  - 问题切得准。type-constrained query 挡得住 control-flow 劫持，挡不住同类型的 value substitution（恶意 clone 链接、lookalike 发件人）。RTC-value 的 78 例专门打这个点，unprotected CUA 在上面 ASR 43.6%/38.5%。CaMeL-CUA 和 UCM 那条"压信道容量"的路线依赖的前提，在这里被实打实地击穿了。这是本文最硬的贡献。
  - 设计上做对了失效方向。用 allowlist 默认全遮，规则缺了损失的是 utility，不会漏放。endorsement 用确定性比对，不再问一个 LLM"这值对不对"。Table 2 的数字把这个取舍摆得很清楚：FNR_free 是 0（UCM 是 44.1%/36.7%），FPR 却高达 76.9%/56.3%（UCM 是 5.2%/4.7%）。这不是"更好的 labeler"，而是把误差全部推到过度遮蔽那一侧。
  - "Zero ASR"是经验结果，不是保证。笔记引的原文写明 endorsement routes 是"against a diverse task set (section 4)"构建的。攻击 suite 和防御路由出自同一组人，co-design 嫌疑明显。没有 adaptive attacker：既没有针对 class/id skeleton 去骗 rule proposer 的 UGC 结构，也没有针对 `recall` 路由的知识误导。安全的地基 FNR_free=0 只在 160 张非对抗的人工标注 capture 上测过。
  - 信任锚自己开了口子。GitHub 承载 UGC，却被当作 reference authority。`recall` 直接信任 P-LLM 的参数知识。RTC-value 的每个例子里，正确值都能从平台上独立拿到。在正确值拿不到的真实场景里，endorsement 只能失败。所以 RTC-value 上的 CR 50.9/69.2 是在对防御友好的分布上测出来的。
  - Utility 的代价被摘要轻描淡写了。"much higher utility"只是相对于 CaMeL-CUA（OSWorld 8.3%）而言。对比 unprotected CUA，UCM-B 从约 91% 腰斩到约 50%。作者把原因归为"依赖无法验证的 untrusted 信息"，但没有拆开结构性损失和 FPR 过度遮蔽各占多少。偏偏后者才是能修的部分。
  - 可比性有缝。specification classifier 拒掉的 generic 任务，在评测中被自动换成 loose 版本，而作者自己说 generic prompt 正是最容易被攻破的设置。原文没交代 baseline 是否用了同样替换后的 prompt。baseline 全在作者自己的 harness 里重跑，CaMeL-CUA 是作者自行适配的。UCM 只比了 labeling，没比 agentic。前沿模型实验只有 10 个人工挑选的 hard 任务，Sonnet 5 的 2/10 除了说明"攻击不是空打"，撑不起别的结论。
- **Rating**: `2` 👀 ，value substitution 这个威胁模型和 robust endorsement 加 allowlist 遮蔽的组合值得直接借鉴，但 zero ASR 是在与防御共同设计的任务集上测的，没有 adaptive attack，而且 utility 掉了近一半，离"安全自主"还差得远。

### EvoUndo
- **Title**: EvoUndo: Recoverability-Constrained Self-Evolution for LLM Agent Harnesses
- **Institutes**: Independent Researcher
- **Source**: [link](https://arxiv.org/abs/2608.28363)  📄 arXiv   **📒 论文笔记**: [[2608-EvoUndo]]
- **核心**: 现有 self-evolving harness 工作（DGM、Harness² 一类）只要 forward 收益为正就接纳修改。EvoUndo 在接纳时多加一道条件：LLM 还要同时合成 witness 捕获程序和 recovery 程序，并且在 counterfactual pre-state 上（IID/OOD 各 20 个，每个 split 至少 19/20）把 harness 恢复到 typed observational equivalence。600 个 zero-shot 任务里有 197 个修改能力为正但无法恢复，常规 verifier-guided repair 在 $L_0$ 下修好 0/197。作者先用确定性 oracle 把失败分层，再跑 2×2 factorial，把失败归到两个瓶颈：诊断粒度（$D_1L_0$ 在 $S_0$ 上 38/48）和 recovery 语言表达力（$D_0L_1$ 在 $S_1$ 上 142/143）。端到端总 yield 从 281/600 提到 461/600。
- **锐评**:
  - 最值钱的不是 EvoUndo 本身，是它的防作弊模板：forward mutation $m$ 锁死在 Turn 0，模型没法把修改弱化成 no-op 来过关；runtime 独立计算 effect，要求 $E\subseteq\mathcal{C}_e$，模型也没法靠缩小 contract 逃检（注入的未声明 effect 300/300 全部检出，0 误报）。"forward gain 且可恢复"这条准入原则可以直接接到 DGM / Harness² 的接纳步骤上。
  - $S_1$ 上的 99.3% 基本是同义反复。$S_1$ 的定义就是"$L_1$ oracle 能解、$L_0$ 不能解"，而 $L_1$ 的五类 primitive 又是对着同一批失败审计出来的（App. C.2）。这个数字只说明 gpt-oss-120b 会用作者递给它的工具。换到 300 个 fresh 任务，Rescue@4 只剩 35%–51%，Middleware 6/50，Multi-Surface 8/50，这才是真实水平。
  - 0/197 有构造成分。$S_1$ 的 143 个在 $L_0$ 下本来就不可解，0/143 是必然结果，真正有信息量的只有 $S_0$ 上 0/48 到 38/48 这一项。verifier-guided repair 全是 0，regeneration 反而有 6/197，这个反常现象作者没有解释。
  - 致命一击是作者自己的 Table 5。selective undo 任务上，effect-scoped snapshot 拿到 300/300 和 159/300，EvoUndo 只有 243/300 和 131/300，而且没有一个任务是 EvoUndo 独赢的。作者说 LLM 合成 recovery 的价值在 snapshot 不可用的场景（不可序列化、依赖状态的 inverse），但实验 harness 全部可序列化，这个场景一个都没测。核心卖点目前没有证据支撑。
  - Benchmark 是作者自建的玩具式 typed state，直接 admissible 率在 family 间从 Config 96/100 到 Middleware 1/100，结果很大程度上由任务生成器决定。负交互（C3，−6.29pp）在 Qwen3.8-27B 上没有复现（+6.25pp，p=0.375），$D_1$ 又是打包诊断，原因无从归因。全文只修 recovery、不动 $m$，"recoverability 和 capability 怎么取舍"这个真问题没有回答。代码也没放出来。
  - 加分项：诚实度很高。snapshot 被支配、holdout 的 precision–coverage trade-off（$Q_{20}$ 下 false positive 降到 0，但 Rescue 从 49.7% 掉到 35.0%）、Wilson/Wald 写错，作者都主动写进了正文。
- **Rating**: `2` 👀 ，准入约束和 $m$-lock / 独立 effect tracking 的设计值得直接借用，但"LLM 合成 recovery"在自建 benchmark 上被 effect-scoped snapshot 全面支配，关键的不可序列化场景完全没有测。

### LoopArena
- **Title**: LoopArena: Benchmarking Models as Runtime Controllers for Loop Engineering
- **Institutes**: DreamX Team, Alibaba Group; Beijing University of Posts and Telecommunications; UNSW Sydney; Data61, CSIRO
- **Source**: [link](https://arxiv.org/abs/2608.28281)  📄 arXiv   **📒 论文笔记**: [[2608-LoopArena]]
- **核心**: 这篇论文把 coding agent 外层 loop 里负责指挥的模型单独拿出来评。Worker（Qwen3.7-Plus）、工具、预算和 evaluator 全部固定，只换 Controller。Controller 读 Reporter 生成的 Evidence Packet，输出 advance / verify / stop 的 Loop Contract，自己碰不到 repo。评测分三档：Type I 是 160 道四选一题，标签靠 replay 执行结果决定；Type II 是 80 个 task slice；Type III 是 80 个完整任务，每个跑 K=3 次。Type III 上最好的 GPT-5.5 也只有 36.25% SSR，每轮固定复述目标的 fixed control 是 31.25%，no control 是 27.50%，GLM 5.2 只有 24.17%，比不加控制还低。
- **锐评**:
  - 最值钱的结论是负面的：Controller 的收益小到快要测不出来。GPT-5.5 比 fixed control 多 12 次成功（240 个 run 里 87 vs 75），每 run 成本却从 \$9.47 涨到 \$34.68。全文没有 CI、bootstrap 或任何显著性检验。Table 14 显示 80 个任务里有 44–53 个对所有策略都是 3 次全败，真正能拉开差距的任务大概只有二三十个。拿这点信号去排 6 个模型，排名本身就站不稳。
  - Type III 的排名几乎全由 SCBench 决定：GPT-5.5 在这个子集上 16/63，fixed control 只有 3/63。BeyondSWE 上所有策略都挤在 17–22/87；LoopsBench 上 fixed control 53/90，反而高过 GPT-5.5 的 52/90 和 Claude 的 49/90。三个来源的结论互相矛盾，论文却给了一个总榜。
  - Type I 的 replay 定标签是全文最硬的设计：4 个候选都实际执行，两套 seed schedule 必须给出同一个唯一 winner，比 LLM-judge 打分干净。问题是在占 42% 的 LoopsBench 子集上，所有 Controller 都只有 26.87%–34.33%，跟 25% 的随机水平差不多，最强的 GPT-5.5 在这里反而垫底（18/67）。可疑的地方有两处：一是 winner 的排序规则（cycle 少、turn 少）奖励的是"省"不是"对"；二是 continuation Controller 在构建时随机抽取，标签可能只反映了那个被抽中模型的后续行为。论文对这个子集接近随机没有任何分析，总体 Type I 准确率被这批题稀释了。
  - "Type II 是廉价代理"的证据太弱：ρ=0.7353 只来自 6 个点，13 对严格有序的 Controller 中有 2 对顺序反转。说 positively correlated 没错，但支撑不了用 Type II 代替 Type III 来排模型。Type I 与 Type III 排序的相关性正文干脆没报。
  - 有几个混杂变量没控制。第一，GLM 5.2 在 Type III 有 271/1,849 次响应耗尽了 20,480 token，只吐出 reasoning、没有答案，被算作协议失败，所以它垫底测到的有一部分是"能不能在预算内交卷"。第二，Worker、Reporter 和其中一个 Controller 都是 Qwen3.7-Plus，存在同族偏置；换 Worker 的检查只用了 4 个 Controller、20 个任务，GPT-5.5 和 Claude 都不在里面。第三，Controller 只能看到 Reporter 的摘要，Reporter 漏报信息会直接算到 Controller 头上，论文没有做消融。
  - 跟同组的 LongHorizonHarness 放在一起看更有意思：那篇用同一个 Qwen3.7-Plus 基座报了大幅提升，这篇在固定 Worker 时只测出约 5 个点。提升可能更多来自 audited state、fresh-context 这类结构设计，而不是 manager 模型强弱（这是推测，两文没有在同一设置下对照）。方向上也和 TeamBench 发现的"Verifier/角色分离收益很小"一致。
- **Rating**: `2` 👀，把 Controller 与 Worker 解耦评测、用 replay 定标签的设计值得借鉴；核心发现"自适应外层 loop 只比复述目标多约 5 个点，成本却是 2–4 倍"有参考价值，但排名缺统计检验、各来源结论互相矛盾、Type I 有四成题接近随机，不足以当 Foundation。
