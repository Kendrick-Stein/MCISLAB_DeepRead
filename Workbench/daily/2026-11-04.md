# 🔪 今日总结

今天 CUA 方向集中出了三篇大系统（CUA-Master、NorthCUA、Harness²），共同点是"harness + 数据飞轮 + 自改进"，共同缺陷也一样：标题主打的递归/飞轮组件都没有被单独 ablate，增益分不清是来自机制还是来自更多数据和更强 annotator。最值得带走的反而是几条干净的对照：ReTrace 证明 CUA 几乎不会自发恢复（恢复要靠 harness 显式触发），Harness² 证明不做 probe 直接让强模型改 harness 会掉 10 分。具身侧 CaPtain 和 VLAGradientRouting 都是诚实的配方拆解，但核心因果 claim 都缺端到端对照或多 seed。

## 论文点评

### ReTrace
- **Title**: Lost in Recovery: Demystifying Recovery Behavior of Computer-Use Agents via Goal-Oriented Action Replay
- **Institutes**: KAIST, ETRI, DeepAuto.ai
- **Source**: [link](https://arxiv.org/abs/2610.27954)  📰 HF Daily ⬆️ 30   **📒 论文笔记**: [[2610-ReTrace]]
- **核心**: 论文把 GUI agent 的"恢复到先前正确状态"从 forward policy 中拆出来单独测量。恢复成功的判定由两部分合取：一是从恢复态重放原轨迹剩余动作后，benchmark evaluator 仍判成功（R_TC）；二是截图 SSIM≥0.99（R_O）。错误态在 OSWorld/WAA 上用 prompt 让 agent 故意走偏 d 步来构造。主要结果有三条。第一，agent 不会自发恢复：Claude-Sonnet-4.6 的 implicit 恢复率从 26.98% 降到 6.37%，EvoCUA-32B 接近 0。第二，显式 recovery prompt 平均提升 17.86%，增益集中在 generalist 模型上。第三，接入端到端流程后，Qwen3.5-9B 平均只涨 +2.12，EvoCUA-32B（54.88→51.55）和 UI-TARS-1.5-7B（17.25→15.74）反而掉点。
- **锐评**:
  - 问题选得准。在 non-web 任务占 87.34%（OSWorld）和 78.72%（WAA）的环境里，URL rollback 用不上，"agent 自己把环境恢复原状"确实没人系统测过。implicit 和 explicit 的对照把"不会恢复"与"会恢复但想不到去恢复"分开了，结论很直接：恢复要靠 harness 显式触发，指望 forward policy 自己想到不现实。这是本文对做 GUI harness 的人最值钱的一条。
  - 核心卖点"截图不够，必须看隐藏状态"被自己的人评削弱了。人评指南第一条就是 Prioritize Visual Similarity。在 R_TC 和 R_O 互相矛盾的样本上，R_TC 单独与人评的对齐率只有 38.8%，还不如 R_O 的 61.2%。拿一个偏向视觉判断的人评，证明不了 R_TC 有必要，正文对此也没有讨论。
  - Oracle 可靠性论证偏弱。胜率只在判定不一致的样本上算（每个 variant 50 个），对 GPT-5.4 evaluator 的胜率是 54.0%，跟掷硬币差不多；κ=0.45 也只是中等一致。用这些数据写 "confirming the reliability"，说过头了。此外 R_TC 实际只看最终任务 evaluator 的结果：如果 evaluator 不检查恢复涉及的那部分状态，误判就会漏过去。
  - 场景是人造的。short horizon 只有 d=1，扰动来自 prompt 故意走偏，并不是 agent 自然犯的错。真实失败往往在多步之后才被发现，副作用也更隐蔽，能否外推不知道。§4 的 ideal recovery 是用 reset 加重放前缀实现的，正是引言批评为不可扩展的那条路，所以它只能给收益上界。
  - Finding 4 说"post-training 削弱恢复能力"，证据是 2 个模型对 3 个模型，模型家族、规模、action space 都不一样，也没有同一 base 模型在 post-training 前后的对比，只能当推测看（作者自己也写了 may）。
  - 端到端数字有问题。Qwen 的 +2.80 只跑了两次，标准差 4.14；Sonnet 的 +1.54 也落在噪声里。EvoCUA 在 Table 9 中 temp 0.0 时 long horizon 恢复率最高（20.63%），端到端实验却把温度改成了 0.7，它的掉点可能有一部分是超参造成的。正文说 EvoCUA 平均恢复率低于 1%，Table 8 四个预算的均值实际约 1.29%。Appendix B.2 说端到端只用开源模型，Table 3 里却有 Sonnet。
- **Rating**: `2` 👀，问题定义和 implicit/explicit 对照值得借鉴，可以拿来做 recovery 环节的独立测量协议；但 oracle 的人评验证跟自己的核心论点相矛盾，端到端增益也落在噪声范围内，不足以改变做法。

### CUA-Master
- **Title**: CUA-Master: Scaling Computer-use Agents through Open-World Recursive Improvements
- **Institutes**: MMLab, CUHK; Tsinghua University; HKUST(GZ); Explore Academy, JD
- **Source**: [link](https://arxiv.org/abs/2611.03126)  📰 HF Daily ⬆️ 97   **📒 论文笔记**: [[2611-CUAMaster]]
- **核心**: 先从 YouTube/TikTok/Bilibili 教程视频里挖 seed task 并重建轨迹，再把 seed 拆成带 precondition/environment/verifier 的 primitive，用 "primitive 数 K × 应用数 N" 两个参数控制合成任务的难度。rollout 失败时回滚到最早分歧步之前的 VM snapshot，保留前缀续跑。外层按每轮模型的失败分析调整下一轮数据配比。从 Qwen-3.5-27B 出发，做 3 轮 SFT（累计约 115K 轨迹）再加 1 轮 RL（约 12K 任务），在 OSWorld Verified / OSWorld 2.0 / WeaveBench / ALE 上得 80.2 / 36.9 / 43.9 / 25.0。hybrid 基准上超过 Qwen-CUA-397B-A17B（WeaveBench 43.9 vs 35.1）。
- **锐评**:
  - 标题卖的 "recursive improvement" 外层飞轮没有被隔离出来。三轮新增数据是 63K → 38K → 14K，分数随数据总量一起涨，却没有等量随机配比的对照，"weakness-guided" 和 "多喂数据" 分不开。失败分析怎么变成数据配比，文中只写了一句 in-house assessment，没法复现。
  - 全文证据最硬的是 snapshot-rollback（Table 3，retry budget 相同）：K/N=40/3 时 rollout 成功率 49.8% vs 14.6%，50/8 时 18.7% vs 0.0%，任务越难优势越大。这是能直接搬走的工程设计。但它只证明了数据产出率更高，没有 "去掉 rollback" 或 "去掉视频 seeding" 后对最终 benchmark 分数的消融，所以每个组件对模型能力贡献多少不知道。
  - "open-world 打破 closed-world 上限" 的叙事被作者自己的 Figure 9 拆了台：annotator 越强增益越大，用 self-policy 当 annotator 增益有限，而 8 个 annotator 角色具体用的哪个模型一个没点名。增益更像是蒸馏了某个更强（可能闭源）的模型，视频提供的外部知识占多少没有量化。
  - 增益来源说白了是 shell。WeaveBench 上 GUI-only 6.6、hybrid 43.9；在 GUI-only 的 OSWorld Verified 上，它 80.2 还输给同尺寸通用基座 Qwen-3.8-27B 的 81.2，作者写成 "comparable"。跨平台也不算赢：WAA 56.2 低于 UI-Mate-27B 的 63.2，MacAgentBench 59.9 低于 Qwen-CUA 的 65.3，表内只有 MacOSWorld 一项是最高。
  - 口径上有几处要打折扣。所有 baseline 都是作者重测的（Qwen-CUA 自报 OSWorld-Verified 86.2，这里重测成 84.0），GUI-only specialist 在 hybrid 基准上用什么 action interface 没说，对手可能被迫用了不擅长的接口。WeaveBench 报的是 average score，不是原 benchmark 的 PassRate。ALE 上和 Kimi-K3、Qwen-3.8-Max 同为 25.0，靠 "full-pass 相同再比 average" 这条附加规则才排到 "仅次于两个闭源模型"。"K=40/N=3 相当于 ALE 平均难度" 没给度量方法。教程视频和 OSWorld 类应用高度重合，全文没有去污染流程。
  - 写作粗糙：图表引用错位至少 5 处（Table 3 写成 Table 7，Figure 8 写成 Figure 9，还有 "Tables 6, 6, and 6"），迭代曲线的数值只在图里，文本核对不了。
- **Rating**: `2` 👀 ，(K, N) 可控合成和 snapshot-rollback 两个设计值得借，hybrid 动作空间的消融也说明了问题，但标题主打的 weakness-guided 飞轮没有对照，annotator 又是黑箱，核心叙事撑不起 Foundation。

### NorthCUA
- **Title**: NorthCUA Technical Report: Turbocharging Computer-Use Agents through Experience at Scale
- **Institutes**: Shanghai Qiji Zhifeng Co., Ltd. (NorthCUA Team)
- **Source**: [link](https://arxiv.org/abs/2611.02102)  📰 HF Daily ⬆️ 30   **📒 论文笔记**: [[2611-NorthCUA]]
- **核心**: 基座是 Qwen3.5 9B/35B/397B 三档的开源 CUA 系统报告，由三块组成。Harness 包括共享 desktop/web runtime、agent-as-a-judge evaluator 和 E2B 批量 rollout。Experience Flywheel 负责造数据：约 40k grounding，Intents/Environments/Verifiers 三条任务构造路线，加上 skill/milestone 引导的难题采集。训练分 Staged Learning 三步：先做 >4M steps 的 mid-training，再用约 3k 条 verified 长轨迹做 SFT，最后在约 2k 个任务上做 joint desktop–web GRPO。Pro 的主要成绩是 OSWorld-Verified 88.6、WebArena-Verified 73.9、SSP 93.3、OSWorld-G 91.0、WebTestBench F1 60.3。另外放出了 Ultrafast choice-head 变体，WebArena 上质量从 64.2 掉到 60.6，换来 2.3× 的提速。
- **锐评**:
  - 这是一份"整个系统加大基座加大数据"的成绩单，不能拿来回答"为什么 work"。overlay、compaction、note 工具、文档消歧 grounding、evaluator 筛选、RSI、segment 规则全都没有去掉单个组件的 ablation。RSI 只有两个 case study，连它贡献了多少条 SFT 轨迹都写着"remain to be reported"。标题主打"co-design"，却没有任何 co-design 和分别设计的对照。
  - SOTA 的口径是挑过的。OSWorld-G 的 91.0 取三次跑里最好的一次，三次均值是 90.2±0.80，只比 Claude Opus 5.5 的 89.9 高 0.3，在噪声以内；而且 Pro 和 Nano/Mini 用的 click schema 不一样。OSWorld-Verified 上比 Qwen-CUA-Max 高 1.0 点，但这是本文 361 任务的 success 对 Qwen-CUA 的 earned credit，口径不同，减出来的差没有意义。OSWorld 2.0 的 30.6 binary 在正文里只拿来和 GPT-5.6 Sol 比，同表的 Claude Opus 5（31.4）、Fable 5（36.1）、Fable 5.1（41.7）都比它高，正文没提。
  - 最大的可比性隐患是污染。Scaling Environments 会从公开 URL 重建网站，而 WebArena 的站点本身就是开源的；RL 任务池又来自"与 SFT 数据关联"的任务。全文对 OSWorld/WebArena 的任务和站点没有任何去重声明，所以 73.9 在可信度上要打个问号。
  - 筛选数据的人没有被检查过。agent-as-a-judge 决定 mid-training 主语料的去留，但论文没报它和人工或 executable verifier 的一致率。这是 ScaleCUA 已经踩过的坑（judge 能执行不等于任务有效）。
  - RL 的增益看不出是否超过噪声。SFT→RL 在 OSWorld-Verified 上只涨 +2.0 到 +2.9，交互式 benchmark 都是单次运行，没报方差；1 个点大约就是 3.6 个任务。Mini 的 OSWorld 2.0 binary 在 RL 后停在 18.5 没动。反倒是 SFT 阶段信息量最大：约 3k 条 verified 长轨迹让 Pro 的 OSWorld 2.0 binary 从 9.3 涨到 27.3，但同阶段 Pro 的 WebArena 只涨了 0.5，desktop 和 web 的数据收益明显不对称，作者没有解释。
  - Ultrafast 的 2.3× 存在选择偏差。耗时只在"所有方法都成功"的 320 题上测，失败任务（通常更长）被排除在外，所以不能当成全分布的加速比。
  - 值得拿走的东西有两样，都不是分数。一是 Experience Adapter 的两条规则：只在 prefix 严格延续时才合并 segment；advantage 和 loss 权重都按完整 attempt 计算。二是用正例、负例、near-miss、合法替代输出四类 probe 测试 verifier。它们相对 ScaleCUA 和 CUAGym 是增量改进，但可以直接迁移到带 compaction 的 agentic RL。cross-site 只有 35.4%、Mini 停滞这类负面信号作者都如实报了，这点值得肯定。
- **Rating**: `2` 👀，open-weight 397B 加开源 harness，以后肯定会被当 baseline，segment/attempt 规则和 verifier probe 也值得借鉴；但没有组件 ablation，污染没讨论，SOTA 靠挑口径撑着，不足以改变做 CUA 的方式。

### Harness2
- **Title**: Harness^2: Recursive Agent Harnessing for an Open World
- **Institutes**: Google Cloud AI Research, Northwestern University
- **Source**: [link](https://arxiv.org/abs/2610.14224)  🔥 HF Trending ⬆️ 68   **📒 论文笔记**: [[2610-Harness2]]
- **核心**: 模型权重冻结，也不用标签。对每个测试任务，方法先跑一次 reference，再提出 invariant 和 domain-specific 两个候选 harness，在同一任务上分别 probe，然后根据行为对比 compose 出新 harness（Propose–Probe–Compose）。每个任务结束后，被采用的 harness tree 和 EXPERIENCE.md 存入 library，供后续任务按需复用。k=1 时，四种 executor×harness 配置下全部超过 base：WorkBuddy-Bench +11.5（GLM-5+OpenCode，64.2→75.7），JobBench +4.5，LAB Partial +11.8pp。k=5 并行递归在此基础上最多再加 3.9/4.2/6.7。editor 和 selector 都是 Claude Opus 4.8，比两个 executor（Gemini 3.5 Flash / GLM-5）都强。
- **锐评**:
  - **最硬的一条是 Figure 7 左的负结果**。不给 reference、probe 和 library，让 Opus 4.8 直接改 base harness，Code 从 73.4 掉到 63.2，Web 从 69.9 掉到 65.0。这说明"让强模型改 prompt"本身是有害的，增益必须靠同任务的执行对比来换。之后做 test-time harness evolution 的工作都应该报告这个对照。
  - **"Open world" 名不副实**。k=1 已经要在可重置的 fresh container 里跑至少 4 次 rollout（reference、两个 probe、composed 再执行），再加 Opus 4.8 的 editor session。有不可逆副作用的部署环境（发邮件、改线上数据、GUI 上点了就撤不回的操作）被这个设定整个绕开了。说到底这是一种 test-time compute 方法，"open" 只等于没有标签。
  - **最该排除的解释还没排除**。base 只跑 1 次，Harness2 跑 4 次以上，最简单的替代解释是"多次采样加 selector 挑"。Appendix C 定义了用同一个 selector 的 Best-of-k baseline，但主表和 Figure 5 在文本可读的部分都没看到它的数值。它是否出现在 Figure 6 里，笔记标为待核，现在不能下结论。"Meta-Harness 算力更多、分数更低"这一说法把离线搜索的成本也算进去了，拿这个口径比较离线方法并不公平。
  - **对 base 稳赢，对强 baseline 未必**。GLM-5+Codex 的 WB-Code 上，Harness2 74.9 低于 Meta-Harness† 76.8；Gemini+Codex 的 LAB 上，75.6 低于 76.5。LAB GLM-5 是 71.4 对 ReasoningBank 71.3，Gemini JobBench 是 36.0 对 Meta-Harness 35.8。测试集每个 domain 只有 25–40 题（JobBench 34 题），SD 在 2–4.5，这些胜负大多落在 1 SD 以内。"consistent gains" 只对 base 成立。
  - **Judge 和 editor 是同一个模型**。JobBench 由 Claude Opus 4.8 打分，editor 和 selector 也是 Opus 4.8，有可能是在把输出改成 judge 喜欢的风格。WorkBuddy 的 judge 是 Gemini 3.5 Flash，它同时又是 executor 之一。Figure 8 的 same-model 实验（Opus 5 自改 +3.3/+5.5/+3.0）回应了"必须靠更强 editor"的质疑，但没有回应 judge 偏好的问题。
  - **标题里的"跨任务递归"证据最薄**。w/o library 在 k=1 下只差 −3.1/−1.8。JobBench→WorkBuddy 的跨 benchmark 迁移在 Code/Web 上只有 +0.6/+0.5，接近噪声。leave-one-out（77.5→79.4）能看到之后任务的 entry，作者自己也承认不是 online 估计。stage instructions 固定不变，被更新的只有 library，所以"改进如何改进"这层递归比 MetaSkill-Evolve 那种 meta-skill 自改写弱得多。名字起大了。
  - **Selector 是明确的天花板**。WB-Code 上出现过选了 55 分、丢掉 95 分的案例，错误前提也会在候选之间传播（损失 2–11 分）。没有 verifier 时，behavioral contrast 挡不住 shared model bias。它和 RHO 的 pairwise self-preference 是同一个死穴，只是换了一种信号。
  - 值得带走的一点：组件 ablation 里 skills/scripts 贡献 −5.3/−3.7，prompt 类只有 −1.5，和 Strong-to-Weak 的 deterministic offloading 归因一致。harness 增益主要来自可执行组件，不是来自提示词。
- **Rating**: `2` 👀 ，"probe 对比优先于盲改"有 Figure 7 左这个干净的对照支撑，值得借鉴；但 Best-of-k 对照缺位、judge 与 editor 同源、对强 baseline 的优势落在噪声范围内，跨任务递归的证据也撑不起标题。

### CaPtain
- **Title**: CaPtain: A Pipeline for Post-Training Code-as-Policy Robot Agents
- **Institutes**: MMLab, The Chinese University of Hong Kong; NovaXBot
- **Source**: [link](https://arxiv.org/abs/2610.40799)  🔥 HF Trending ⬆️ 20   **📒 论文笔记**: [[2610-CaPtain]]
- **核心**: 作者把语言 agent 常用的"固定 harness 内 SFT + multi-turn RL"配方用到 code-as-policy 机器人操作上。Qwen3.5-4B 只能调用 22 个低层感知/测量/guarded-motion 原语来写 Python，没有 grasp/place 宏，也没有 VLA。RL 阶段的 critic 读取仿真器的 36 维特权物理状态，是 5 个 MLP 的 ensemble。它用同一时间索引 t 的 ΔV 给每个 request 分 credit，因此纯感知 request 的 δ≈0，测试时 critic 去掉。结果是 held-out LIBERO 从 0% 升到 55.4%（SFT），再升到 73.8%（RL），LIBERO-PRO 3-suite 78.5%，三个扰动 suite 上 RL 增益为 +17.6 到 +21.2 点。zero-shot SimplerEnv 83.3%、CaP-Bench 75.0；RoboTwin 2.0 Hard 只有 22.6%，RoboDojo SR 0.8%。
- **锐评**:
  - 标题级贡献缺最关键的对照。全文没有一组实验在同一 pipeline 里把 critic 换成 outcome-only GRPO 训到底再比最终成功率。critic 的价值只靠离线证据支撑：gradient-noise scale 从 9.0k 降到 6.7k，只降约 26%，而且 λ=0 时是 12.6k，比 GRPO 还差，说明有效成分可能主要是 GAE 平滑，而不是"特权 ΔV"本身；另一项证据是 |A| 质量分布（motions 65%、感知 1.3%）。73.8% 里有多少来自 critic，有多少来自"任意 multi-turn RL + 1,024 episode 累积 + 精心设计的成本项"，目前分不出来。
  - "SFT→RL +18.3" 不是干净的 RL 增益。SFT 数据里有 6.1%（1,386 行）是 RL 策略自己的成功 rollout，critic 也在更早策略的 episode 上做了 warm-start，所以 SFT 基线已经吃到了一部分 RL 的产出。
  - "held-out" 的范围很窄。RL 在全部 40 个 LIBERO 任务上训练，held-out 只是同一批任务的未见初始状态；PRO/Plus/MAX 也是在这 40 个任务上加扰动。所以"扰动下增益保持"说明的是对视觉和布局扰动的鲁棒性，不是任务泛化。另外，Figure 7 的选模评测包含 40 个官方 seed-11 episode，而 seed 11 属于 11–16 的评测集。原文没有说这构成泄漏，"测试集参与选模"是我从这两处设置推出来的，影响多大没有证据，但作者提供的 seed-11 子集（74.6%）恰好就是选模用的那个 seed，消不掉这层疑虑。
  - "no frontier model" 要打折扣。861M token 的 SFT 数据里 654M 由 GPT-6 Astra 生成，本质是 frontier 蒸馏；感知还依赖 SAM 3 和 Molmo2-8B，$0.03–0.06/episode 不包含这部分成本。拿它和 OpenRUA 的 $8–22 比，不是同一口径。
  - Table 2 的比较只能看量级。基线数字取自各自论文，turn budget、oracle 信号、GT depth、试验次数都不同。78.5 比 K1 的 77.2 只高 1.3 点，在这种协议差异下谈不上"超过 frontier agent"；同表里 OpenRUA 91.8、AgenticRoboRL 81.3 仍明显更高。+19.4 对 AgenticRoboRL +5.9 的"skill 层封顶"论点，起点相差 16 点（49.2 对 65.1），低起点涨得多本来就不奇怪，作者自己也承认这一点。
  - 真正值钱的是负面分析，不是主表。给 critic 喂 LM hidden state 后，35% 的 |A| 质量漂到感知 request 上，因为 hidden state 能线性解码出 request index（R²=0.80），作者还排除了策略行为计数器这类时间代理。这条"critic 输入会通过时间泄漏污染 credit"的教训，对 GUI agentic RL 里同样有后端特权状态的仿真环境可以直接借用。布局记忆的发现（官方 1.4 cm 方差导致坐标似然与图像无关，改成 15 cm wide-layout 才恢复 grounding）也是能复用的硬结论。
  - 适用边界很清楚，而且偏窄。位姿噪声加到 5 cm 时，与特权 ΔV 的相关只剩 0.36，改用策略自身感知时只剩 0.21，这条路线目前无法在真机上在线 RL；真机部分只有两个定性 episode，没有成功率。双臂同时运动的任务 0/35，Wipe 这种持续力控任务在 guarded Cartesian 原语下根本表达不了。统计口径值得肯定：McNemar 配对检验，区分 host 和 strict success，如实报告 Long +13.3（p=0.13）和 MAX Dynamic strict（p=0.15）不显著。
- **Rating**: `2` 👀 ，这是一套诚实、可复用的完整工程配方，固定 t 的特权 ΔV credit 和 hidden-state 泄漏分析值得借鉴；但"critic 是关键"缺端到端 ablation，SFT 基线混入了 RL rollout，held-out 只到初始状态这一层，核心因果 claim 还没站住。

### VLAGradientRouting
- **Title**: Should the Action Expert Train the VLM? Action-Token Supervision and Gradient Routing in Mixture-of-Transformer VLAs
- **Institutes**: NVIDIA, Princeton University, Stanford University
- **Source**: [link](https://arxiv.org/abs/2611.05249)  📄 arXiv   **📒 论文笔记**: [[2611-VLAGradientRouting]]
- **核心**: 在 VLM + flow-matching action expert 的 MoT VLA 上做 2×2 因子实验：一个因子是 VLM 有没有 discrete action-token CE 监督，另一个是 expert 的 flow loss 梯度回不回传 VLM（coupling 对 Knowledge Insulation 的 stop-gradient）。driving 上还加了三种训练 schedule。结论是这两种信号可以部分互相替代。没有 action token 时，coupling 让 open-loop ADE 降约 26%/24%，AlpaSim route progress 从 0.425 升到 0.601。有 token 时 open-loop 基本打平，但 concurrent closed-loop 仍是 coupled 更好（0.600 对 0.703）。PolaRiS manipulation 上，π0.5 复现和 MolmoAct2 两个模型族的最佳配置都是 coupled + FAST off（32.9% / 36.5%）。
- **锐评**: 问题问得准。KI 把"梯度阻断"和"FAST 辅助监督"打包成一个 recipe，大家抄了却没人拆开测过。本文用前向完全相同、只切反传的 sg(H) 来拆，控制也做得细：CE 分母固定，expert K/V 截止在 `<future_start>`。这种拆 recipe 的工作比又一个 +0.3% 有用。问题是标题问得很大，证据撑不起反 KI 的口径：
  - **最该打的那一格没打赢**。π0.5 / MolmoAct2 实际用的是 VLM-First + token。这一格里 closed-loop 是 0.648 对 0.646，完全打平，而且 coupled 的 at-fault collision 从 0.076 涨到 0.117（Expert-First 是 0.061 到 0.097）。manipulation 只跑了 concurrent，KI 真正用的 staged 设定一次都没测。证据能撑住的说法是"concurrent 训练或者不用 action token 时，insulation 不划算"，撑不住"insulation 不该是默认"。
  - **KI 的收益一侧没测**。KI 的初衷是保住通用 VLM 能力，本文只拿 driving rationale 的 Lingo-Judge 当诊断，没报任何 VQA 类通用 benchmark，manipulation 模型的 VL 能力完全没测。只量代价不量收益，就下"insulation 不值"的结论，等于缺席判决。何况 Lingo-Judge 在两种 staged 无 token 设定下都偏向 insulated（0.630 对 0.613，0.620 对 0.612），刚好是 insulation 可能有用的信号，被放过了。
  - **单 seed，每个条件 15k GPU-hours，只跑一次**。bootstrap CI 只覆盖评测 clip 的方差，不覆盖训练方差。closed-loop 和 manipulation 连 CI 都没有。22.0% 对 24.3%、0.648 对 0.646 这类差距不能当结论用。PolaRiS 每个环境只有 50 次 rollout，三个环境。
  - **progress 和安全指标走反方向**。concurrent + token 下 coupled 的 distance to GT 是 2.700，insulated 是 2.378，偏得更远，collision 也没改善。"coupled 更好"主要是 route progress 一个指标给出来的。作者自己报出了这点，算诚实，但正文结论没因此收紧。
  - **schedule 比较有混杂**：总步数对齐了，expert 实际更新次数却在 97k 到 197k 之间。VLM-First 下 token off 的 warm-up 只看 VL 数据，token on 还会看到 trajectory 数据。"Concurrent 最优"不能干净地归因到训练顺序。
  - **跨领域一致性打了折扣**：driving 关 token 用的是 mask 但保留 teacher-forced 序列，manipulation 是直接删掉 FAST postfix，干预方式不一样。manipulation 的绝对水平也偏低（最佳 36.5%，低于官方 π0.5 的 40.0%，不过协议不同），换成 10k 小时级的大规模预训练，routing 效应还在不在不知道。全部是仿真，没有真机，也没有表征探针或梯度冲突分析，"partially substitutable"只是对现象的描述。
  - 值得带走的是一条可操作的判断：先看 VLM 有没有直接的 action 监督，再决定 routing。没 token 就 couple，这条在两个领域、三个模型族上方向一致（coupled 无 token 0.601 ≈ insulated 有 token 0.600）。DM0 这类"KI + action token"的做法正好落在本文"代价小"的那一格，可以对照看。
- **Rating**: `2` 👀 ，因子拆解干净，"没 token 就 couple"这条结论跨领域可复用；但 KI 实际使用的 staged + token 设定上打平且安全指标更差，保留 VLM 能力那一侧完全没测，又是单 seed，撑不起标题里的反 KI 结论。
